# Office 能力可靠性与核验实施方案

> 状态：核心实现已落地，按底层失败机制收口，未闭合项保留。制定于 2026-10-29，按评审和产品目标修订于 2026-10-30。本文不是 decision record；Office 产品目标与支持范围以产品需求为准。本方案定义实施安排，涉及长期合同变化时更新对应真源。

## 1. 目标与完成标准

本轮以[产品需求定义的可用、好用的 Office 能力](../requirements.md#53-task)为目标，建设 DOCX、XLSX、PPTX 的可靠执行、生成一致性和可验证交付流程。#23、#28、#71 是首批验收场景，方案的结构按失败模式和 owner 划分，各项实施结果都要落实到真实用户任务。

预期结果：

1. 普通工具失败、依赖缺失、权限拒绝和用户取消都有明确且正确的运行结果；真实协议违约保持 fail-closed，对能够关联到本 Run 的拒绝保留发生边界与约束事实。
2. 固定创作依赖、随包示例、读取脚本与检查器共同通过代表性特性的创建、修改和再次检查。文件可写出不能替代能力链通过。
3. 文档检查直接读取最终候选文件，对明确的检查范围、预期和实际结果给出机器可复核的证据。内容、样式、结构和查看器兼容性分别报告。
4. Skill 的交付说明由实际检查结果支持。未执行、未支持、失败或失效的检查不能被表述为已通过。
5. 同一失败模式由唯一生产实现和对应测试保护。共享文档脚本有唯一源码；三个物化 Skill 继续自包含，不依赖彼此的临时资源目录。

系统交付分为运行可靠性、文档检查能力、创作链资格和真实模型工作流四类结果，分别结算。任一类未完成，不能用其他类的通过替代，也不能报告整个专项完成。

“可用”的验收重点是：已支持的读取、新建、定向修改和交付任务实际完成，数值、内容与指定格式正确，原件得到保护，必要检查有真实结果。“好用”的验收重点是：用户描述目标并提供必要材料后，系统组织环境准备、处理、核验和交付；正常流程无需用户补充内部安装路径、手动修 XML 或编写处理脚本；必要的授权、澄清和失败后续操作清楚可理解。各格式的模型任务验收须同时观察这两方面；出现依靠用户补充内部实现知识才能继续的情况，应登记为流程缺陷，不能只记录最终文件生成成功。

## 5. 共享资源的唯一源码

将三份 Skill 中实际相同的 scripts/office 资源收敛到 Product Skill 内的唯一源码目录，建议使用 src/product/skill/office_resources。格式专属内容仍跟随对应 Skill；例如 XLSX 的公式辅助脚本不能因为共享目录调整而变成三格式共同实现。

构建器从唯一共享源码和格式专属输入生成每份完整资源包，继续保持物化后的 scripts/office 与 environment 路径。共享源码和专属源码发生目标路径冲突时构建失败，不采用静默覆盖顺序。运行时不跨 Skill 查找脚本，不从临时目录父路径反推公共根。

有界归档处理仍只消费 [canonical archive helper](../../src/product/control/resources/archive.py)，不把已有生成副本提升为另一份 authority。B 只归一源码和必要的生成目标定位，保留 sync-office-archive.mjs 及其 --check 调用；包内 archive.py 的历史生成注释原样保留。如果生成副本搬到共享源码位置，同步脚本只改为维护这一份共同生成副本，不能保留多份手写来源或使现有检查入口失效。

B 之后第一个因功能变更需要重建 archive 的提交，再由构建器直接从 canonical helper 派生所需包内入口，并同步更新生成注释、删除旧同步脚本及失去职责的生成副本、收口相关调用与 guard。注释更新和 archive 重建在同一提交完成，不把该清理列为独立前置工作包；无论先重建的是 E-XLSX 还是 D，都由该提交完成。这样 B 不需要制造一条指向已删除脚本的注释，后续也不保留两条 active 生成路径。

新增检查工具复用现有严格解析器、归档保护和固定运行入口。结构检查的公共实现只保留一份，validate/pack 和新工作流调用同一实现；已有 CLI 各自的读写职责保留，重叠的规则调用共同实现，不要求为形式上的统一再增加转发层。没有现存调用或合同职责的重复入口才删除。

纯源码归一单独提交，保留现有资源 archive 原字节，不因源码搬迁发布新资源目录。除包内路径和内容外，构建器还须保持 tar 成员顺序、header 与 padding；用现有 --check 将新源码生成的完整 tar 与原 archive 解压结果逐字节比较。仅文件清单与内容相同不足以证明 archive 身份不变；B 的退出条件包含该完整比较，新增功能另在后续提交按固定生成工具重建 archive。目标依赖身份不因纯源码搬迁改变。相关结构 guard 只调整源码定位，不改变既有拒绝政策；保留反例验证，不能借迁移删除失败断言或扩大 allowlist。

此调整属于同一 owner 内的源码收敛，不改变已发布依赖来源、Workspace 权限或临时物化生命周期。Skill 资源内容更新不应单独触发解释器重新下载；若依赖锁变化，则由现有身份构造自然生成新的环境身份，不修改既有正式目录。

新增 XLSX 文件的提交会改变整个 Office archive 的摘要，Application 因而会发布新的整包资源目录。格式工作包独立不等于资源发布完全隔离：对比变更前后的包内映射，确认 DOCX/PPTX 及共有执行说明没有意外内容变化，并运行现有发布/catalog 边界的定向回归，确认三项 Skill 仍完整、自包含、可寻址。该回归不要求已有缺陷的 PPTX 通过结构校验；若确实修改了共享执行代码，则按实际影响追加格式回归，不把新目录本身当成新解释器环境或新增审批对象。

## 6. 通用运行可靠性

### 6.1 首次失败与收口事实

复用现有 termination latch、Run projection failure 和 terminal publication。只在相应 owner 内增加定位所需的有界信息，不建立横跨所有 owner 的可变全局诊断对象。

诊断至少回答：观测到的拒绝发生于 callback admission、event decode、pump/notifier、Task event application，还是 terminal drain；事件种类与受控错误类别是什么；匹配用的 Run/Session 身份是否有效；输出片段的序号、turn/group、字节计数在哪个约束上不符。

Agent 的首个拒绝事实与 Task 的后续收口结果分别保留。终态发现未闭合片段时仍执行当前清理和 fail-closed 合同，同时提供足够信息表明这是收口发现；不能用它覆盖更早已知的 callback 原因。没有捕获到首因时明确未知，不从诊断字符串猜测。

“首个拒绝”只表示该 owner 在其同步边界内最先保存的观测，不等于跨线程、跨 owner 的真实根因。仅凭时间戳、回调到达或 latch 的写入先后不建立因果关系；分析应使用可证明的身份关联、事件顺序及调用前后关系。无法确定两个并发错误的先后或因果时保留这份不确定性，不建设全局事件时间线来推测根因。

诊断采集复用现有锁和预留的固定容量，不在 callback 中增加文件 I/O、同步日志、额外 event consumer 或依赖主线程的等待。诊断空间不足不能造成新的 callback fatal，也不能把旧诊断覆盖为后来的故障；保留不可用/截断事实即可。termination latch 的优先关系、terminal outcome 和 disposition 仍由现有 policy 决定，新增观测不擅自改写这些语义。回归用诊断开启/缺省/容量不足三种条件对照运行结果和资源释放。

诊断只包含 typed 分类、数值和有界状态；不记录正文、private reasoning、原始工具参数、认证内容或用户文件内容。尽量使用现有安全诊断出口；若现有出口的合同不能承载所需事实，先提出精确合同变更，再同步实现和验证，不顺带扩展历史 schema、Bridge 或 Snapshot。

### 6.2 受控复现与修复决策

走正式 Agent Session、event pump、Product drain 与 Task projection，覆盖成功工具、非零退出、缺依赖、权限拒绝、模型流中断/重试、工具前后 commentary、取消和跨轮继续。Office 脚本只作为其中的实际工具载荷。

| 首个失败位置                               | 修复责任与方向                                                                                                                         |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 合法事件被 Host 解码、身份或时序检查误拒绝 | 修复对应 Host owner 的合同消费；保留非法输入拒绝与生命周期屏障                                                                         |
| Core 发出了违反已接受 ABI 的序列           | 在当前锁定 bundle 内 fail closed，记录 typed 拒绝事实与精确 artifact 身份，必要时形成最小复现；不规划或依赖本仓库之外的 AgentCore 修复 |
| 事件合法，Task 的分组/字节或终态处理错误   | 修复 Task 状态转换及 drain 编排，追加竞争和边界回归                                                                                    |
| callback 已失败，未闭合片段只是后果        | 保留首因与清理事实，修复实际 callback 原因；不靠跳过收口取得成功                                                                       |
| 当前无法复现或只能看到历史摘要             | 保留未闭合结论和诊断手段，不宣称已修复，不增大超时或反复运行碰运气                                                                     |

跨轮执行前，Skill 必须重新取得当次有效资源入口；对话下载同意与 Shell/文件权限继续各自生效。该流程要求不授予持久 activation lease，也不自动重放一次已经产生效果的准备或编辑操作。

## 7. 创作依赖与检查器的组合资格

### 7.1 固定输入的接受标准

依赖的接受单位是正式发布 artifact 与锁定依赖组合。包能安装、模块能 import、文件能写出只是前置检查。用于随包教学和默认生成的特性必须在该组合上完成实际生成、结构检查、内容/关系检查、定向修改与再次检查。

优先消费满足要求的 canonical 上游修复发布，并对最低系统、现有目标、锁、下载量与环境身份按实际变化验证。不得修改 node_modules、复制依赖源码、消费可变分支或以全局包替代固定输入。未取得可接受修复版本不构成放宽检查器的理由。

### 7.2 PPTX 的确定处理步骤

先核对校验适用范围：文档使用的格式/namespace、被选中的 Schema、检查器的预处理和已支持特性是否匹配，区分适用范围内的真实结构违约、错误选择/使用 Schema，以及检查器尚未覆盖的特性。修正 Schema 匹配错误时保持原接受合同，并用合法与非法反例证明没有放宽政策；若结论需要改变已登记接受政策，另按明确授权与真源变更处理，本轮不预先执行。生成器差异不能仅因“已知”就从失败改名为未支持。

把当前问题拆为三条独立约束：presentation 的备注列表顺序、bar series 数据点与标签顺序、二维图表的轴引用数量和引用完整性。用文字页、有/无备注、默认/多色柱状图及线图等最小样本定位各约束的触发条件。检测引用应按实际定义和关系工作，不能硬编码本次生成器碰巧使用的轴 ID。

检查正式修复发布能否同时满足这些约束。图表结构约束与备注处理的兼容风险分别验证，前者不等待后者才能开展修复。拟采用的备注顺序变更已有上游兼容性疑点，因此该决策需要真实 PowerPoint 或可独立复核的、覆盖同一受测特性的兼容性证据；其他查看器的打开结果不能替代 PowerPoint 结论。源代码中的兼容性注释也是线索，不能据此豁免 Schema 错误。

如果正式发布输入仍无法满足要求，在依赖决策阶段评审显式的 Product Skill 文档处理方案：只处理本流程新建的工作副本、只变更已定义且可验证的结构、先验证变换前提、变换后重新执行原严格检查。该方案属于对生成文档的处理，不是修改依赖实现；是否采用由结构和查看器证据决定，不能把本次诊断副本的改写直接作为默认生产路径。

若采用文档处理，只有一条 canonical 生成后路径；未知结构、前提不满足或处理失败明确失败，保留原件与诊断，不静默降级为删图表、删备注或交付原失败文件。若无法证明必要语义和兼容性得到保留，记录真实能力缺口，本轮不得宣称该组合通过。

现有文档的编辑另遵守原件保护与已有结构缺陷比较语义。原件已有错误、修改未增加错误与新文件完整结构通过是不同结论；不能用 original 参数把新建坏文件自比为通过。

## 8. 有限、可执行的文档核验

### 8.1 工具形态

在 Product Skill owner 的 XLSX 专属脚本内提供一个固定私有 Python 调用的检查入口，建议包内位置为 xlsx/scripts/verify.py。入口接受 XLSX 候选文件、有限的检查说明和新的报告路径。由固定版本的代码解释检查，不提供任意表达式、脚本插件、动态包或可执行公式求值。

该脚本一律经所属 Skill 的固定 run 入口调用。现有 run.py 会先将 environment 目录加入 sys.path，再执行目标脚本，因此 scripts 下的入口可直接导入 environment 中由 canonical helper 派生的 office_archive；不依赖当前目录、系统 Python 或额外 PYTHONPATH。E-XLSX 的真实入口资格须覆盖这一导入关系。

新增实现只覆盖 XLSX 实际缺少的范围断言与报告；DOCX/PPTX 不接入该入口，继续使用已有格式检查。D 闭合后若确有需要，可在 F-PPTX 内复用已证明适用的结果表达，但不以接入新入口作为完成要求。不在一次检查中重复解包、解析同一文件，不为未来复用先建立通用报告框架。

具体 CLI、字段名、退出码和预算在实现与 fixture 中唯一定义；本计划只确定语义。unknown check、格式不匹配、损坏说明、超出格式坐标界限或检查预算均明确失败，不能跳过后输出总体通过。合法选择器要求的目标缺失属于检查不满足，不因它超出当前 sheet 已使用区域就当作说明语法错误。生产入口先保证无业务检查说明时仍执行已支持的基础检查，并明确业务要求未核验。

入口无依赖下载、无 Office 自动修复、无文件覆盖。修正文件是明确的创作/编辑步骤，完成后重新检查。报告与候选文件分开写入新路径，失败或中断不能发布看似完整的成功报告。

检查执行结果与文档是否符合要求是两个事实，调用方按以下分类处理，不把任意非零退出都解释为“文档需要修改”：

| 结果类别                                             | 允许的后续动作                                                                                                                         |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 检查已完成，明确断言不满足，包含必要目标缺失         | 核对预期来源；候选确实违反任务要求时修正授权范围内的候选，再复验。确认是说明误写时只修正说明的表达，不将预期值改成实际错误值来获得通过 |
| 检查说明语法非法、操作未知或选择器超出格式/预算界限  | 修正说明并保留原任务要求；不能删除失败项、缩窄必要覆盖范围或据此直接改候选                                                             |
| 必要检查未支持或无法执行                             | 明确未完成项与限制；不转换为成功，不无限重试                                                                                           |
| 运行时缺失、权限拒绝、文件 I/O、预算或检查器自身异常 | 沿已有环境/权限和失败说明处理；不自动修改文档、不更换依赖来源、不把它包装为内容检查失败                                                |

状态与退出码的具体表达由实现及 fixture 唯一声明。修正/复验沿既有 Run 执行预算进行；候选、检查说明和失败条件都未变化时，不重复执行相同检查来等待偶然成功，也不增加后台修复循环。

### 8.2 检查责任

| 检查类别         | 确定性工具检查什么                                                             | 不能据此声明什么                             |
| ---------------- | ------------------------------------------------------------------------------ | -------------------------------------------- |
| 基础可读性与归档 | 受限 OOXML 归档、选定库可读取、必要 part 与引用                                | 全格式保真或任意查看器兼容                   |
| 已支持结构       | 复用 DOCX/PPTX validator 的支持范围；PPTX 图表轴和关系完整性                   | 所有 XML part 均完整验证或实际渲染正常       |
| XLSX 内容        | 指定 sheet、坐标/范围、类型、保存值、公式文本和独立预期结果                    | 公式已执行、缓存为最新或任意业务规则正确     |
| XLSX 样式        | 指定范围的字体属性、数字格式、填充和合计位置等明确要求                         | 文件中任意对象的视觉效果正确                 |
| DOCX/PPTX 内容   | DOCX 段落/表格/section 的结构与顺序；PPTX slide 顺序、文本、备注及定向编辑要求 | 实际分页、图表外观、文本不溢出或字体实际可用 |
| 修改保留         | 用户要求保留的内容、关系、公式和样式，按明确范围与原件比较                     | 任意未解析特性完整保留                       |
| 视觉与查看器     | 本轮自动工具明确标记未执行；资格阶段另取真实查看器证据                         | 从结构/文本检查推导视觉验收                  |

XLSX 首期围绕数据清洗、汇总和针对性修改实现有限检查族：sheet 存在/顺序、范围值与公式、唯一合计标签及坐标、指定数值容差、字体、填充、数字格式、原件与指定不变范围。表中的 DOCX/PPTX 能力说明用于区分现有检查责任，不表示 E-XLSX 要实现三格式统一报告，也不改变既有格式的交付前置条件。

现有 read.py 继续提供结构化内容读取，不把它的成功解释为样式通过；XLSX 没有完整 XSD validator 时如实记录实际基础检查方法，不补造“三格式 XSD 全通过”的摘要。

样式检查只判断文件中存储的属性：字体属性不证明字体实际安装或被查看器采用，数字格式字符串不证明公式已计算或查看器显示值，主题/索引色不能未经解析就当作直接 RGB。首期只支持明确可判断的表示，遇到当前实现不能解释的主题、条件格式或样式组合时返回具体未支持项，不自动改成等价格式或强行通过。数值比较需指定类型和容差；空值、布尔、非有限值与数值零不能互相替代。

选择器本身也必须受检：缺 sheet、唯一标签没有命中或命中多处、要求非空的范围实际为空，都不能因循环没有执行而通过。允许空数据集的情况由明确的数量/空集预期判断，报告实际匹配数量，不把空集合上的属性检查解释为全表字体或合计检查通过。查找范围限定到任务指定的表或区域，不能搜到其他说明区中的同名“合计”后继续验证错误对象。

### 8.3 预期值的来源

检查说明由用户要求、原件保留要求和明确的业务计算产生。模型可以编写检查说明，但说明自身不是独立真值，也不具有权限。对于“所有数据和合计使用指定字体”等要求，必须明确覆盖范围和合计定位；只检查 A1 不满足该要求。

在生成前，将实际任务的必要要求对应到计划检查或明确的未支持项，记录预期来自用户原话、原件，还是独立计算。该对应表可以作为检查说明的一部分，属于普通 Workspace 工作文件；它帮助发现遗漏，但不能由程序证明自己完整覆盖了原始自然语言任务。报告把“全部已声明检查通过”与“用户要求覆盖情况”分开表达；未映射、未执行或不支持的必要项不能被删除以获得成功摘要。没有业务检查说明时只能声称基础检查结果，不能输出任务完成的质量结论。

生产示例在追加合计行后保存实际坐标，并对标签唯一性、范围和格式做断言。检查器不能只相信生成脚本回传的 total_row；应重新读取标签/结构并与任务预期交叉核对。数值预期优先从原始输入按独立方法计算，避免生成器与核验器共享同一个错位变量。

正式测试使用合成输入和独立 oracle。将一处必要样式、合计位置、数据值或关系故意破坏后，保留的权威检查必须失败；仅测试“生成器产生了自己预期的报告”不能算覆盖。

独立 oracle 的职责是判断任务预期，不复制生产检查器。测试中从合成输入的原始行独立计算清洗数量、金额与分组，直接打开产物检查必要属性；选择器、样式读取与汇总计算不能原样复用生成脚本的函数。原件比较只检查声明应保留的语义和部件，不以 ZIP 字节相等代替内容保留，也不因合法序列化差异误判修改失败。

### 8.4 报告语义与字节绑定

报告最少描述：被检查候选的大小和 SHA-256；实际检查方法；每项检查的目标与范围、预期/实际、通过/失败/未执行/不支持及原因；完整执行与详情截断事实。只有候选摘要用于与实际 DeliverFile 回执比对；检查说明和参考输入没有持久化摘要的消费步骤，不在报告中为它们新增身份绑定。报告中的要求对应关系以已提交的说明为范围，不宣称自动证明了用户任务的语义覆盖。

检查通过与失败都关联同一份实际读取的受检字节。复用有界 checked copy，摘要与检查针对同一副本；检测受检输入变化，禁止在异常路径留下成功报告。检查完成后只要候选再被编辑，先前报告立即成为旧字节证据，必须复验。

检查说明先有界读取并固定为一个版本，参考文档也使用受控副本；同一执行不能混用变化前后的输入。报告用独占创建写入新路径，例如 open(path, "x")，任何已有路径均拒绝；不使用先检查 exists 再覆盖写入的流程，也不另外建立文件别名检测。报告写入失败与业务检查失败分开，截断或中断报告不能被读取为完整成功；只有声明的必要检查全部执行且通过时，才允许产生对应范围的成功结论。进程退出为零也不表示未声明的业务要求或视觉检查通过。

报告可包含任务要求检查的文档内容，因此仅留在用户授权的 Workspace，按普通敏感任务文件处理，不写入应用日志、不自动作为成果交付、不进入 Snapshot。默认 stdout 只返回有界状态、摘要和报告位置，不输出检查项中的原始文档值；脚本错误与预算失败也不能绕过该边界输出原始 XML 或全文件正文。

对检查说明、归档、XML、单元格遍历、比较范围、失败详情、报告大小和运行时间分别设有界预算，复用适用的既有 limits；未知或稀疏超大范围要在昂贵分配前拒绝。容量截断必须保留准确状态，未完整执行不能得到通过。不会通过扩大产品共享容量来容纳不受限的检查报告。

## 9. 按格式推进工作流与交付

### 9.1 共有说明不携带格式专属门槛

三项 Skill 继续从同一 EXECUTION 源取得环境、下载同意、权限、原件保护及现有 DeliverFile 调用方法。构建器会将这一说明嵌入三份 SKILL.md，因此新增 XLSX 检查步骤只能写在 XLSX 专属 SKILL.md 与示例中；不能在 EXECUTION 增加统一的“必须运行新检查入口后才能交付”，也不引入按运行时状态切换检查政策的开关。

| 格式 | 本轮实施方式                                                                                       | 与其他格式的依赖                                                                          |
| ---- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| XLSX | E-XLSX 完成后，F-XLSX 独立接入新检查与交付说明                                                     | 不等待 C 的诊断能力或 D；若实际运行遇到 #23，只按真实失败阻塞该次验收，不预先建立文档依赖 |
| DOCX | 保留已有创建、修改、validate/read 和交付流程，只回归共享资源调整实际影响的部分                     | 不等待 D 或新检查入口                                                                     |
| PPTX | D 闭合前保持现有 SKILL.md 的 validate/reopen 和交付流程，不接入新增检查门槛；D 闭合后再推进 F-PPTX | F-PPTX 依赖 D，F-XLSX 不依赖 F-PPTX                                                       |

保留 PPTX 现有流程不等于现有文件已通过严格校验，也不关闭 #28。已有 validator 的失败仍原样失败，不能改称“未支持”或登记为通过；本轮只避免因 XLSX 新机制给 PPTX 追加一个普遍无法满足的门槛。PPTX 检查适用范围的判断属于 D，未完成前不修改准入政策或失败语义。

### 9.2 XLSX 的增强流程

以下步骤仅由 F-XLSX 接入：

1. 从用户任务与原件确定输出、必须保留的内容及可检查要求；对不能确认的要求明确说明。
2. 获取当前 XLSX Skill 的有效入口，按实际缺失环境沿既有同意和权限机制准备。
3. 在 Workspace 工作副本中创作或修改，保留原件。
4. 用 XLSX 检查入口检查最终候选；读取报告并按 §8.1 分类处理。只有已完成的检查和任务要求共同确认候选不符合要求时，才据此修正候选并对新字节复验。执行异常或必要检查无法完成时报告真实阻塞，不把未完成结果作为成功交付。
5. 在交付前确认候选仍对应本次检查的字节；调用既有 DeliverFile，依据真实回执登记成果，并比较回执中的大小与摘要和报告中的候选身份。
6. 最终说明分别陈述文件交付结果、已通过的检查范围及未执行项。需要交付检查报告时，依用户要求单独交付，不默认附加包含文档内容的报告。

### 9.3 报告与 Host 回执的边界

检查报告是 Workspace 内可复核的工作文件，不是 Host 颁发的可信凭据。DeliverFile 继续只证明其现有文件身份、稳定读取与回执提交事实，不读取模型自报状态、不把 verify 报告提升为 authority，也不更改 tool schema。

检查与交付之间没有新增的原子事务，交付前一次摘要比较不能排除随后的文件变化。回执摘要不匹配时保留真实交付事实，明确原检查不覆盖已交付字节；需要再次检查并按真实结果说明，不自动删成果、不自动重发 DeliverFile，也不能声称已经通过质量检查。

Office 工作流以真实任务结果验收。Agent 组织已支持的文档操作和必要检查，脚本执行确定性处理与核验，Host 管理权限、运行生命周期和文件交付；各层按自身职责提供准确结果。模型漏调必要检查、误读报告或作出无依据的成功声明，都属于需要修复并进入回归的工作流缺陷。报告与 Host 回执的权限边界继续成立，产品质量通过端到端任务验收落实。

### 10.1 缺陷验收与后续稳定性评估

2026-10-30 用户批准按原始缺陷及最小充分回归分别结算，不再以完整模型矩阵阻塞每个 issue。该调整只适用于之后的收口：既有冻结任务、失败、人工介入及未验收记录原样保留，不把旧矩阵改报通过，也不弱化生产检查器或文件断言。

本轮按底层失败机制与 owner 分成三条独立证据链；issue 只提供反例，不要求机械复刻原步骤，也不把某条复现步骤正常当作底层故障已修复：

- 创作链一致性（#28 线索）：原始三处结构缺陷可重复，新建生产路径处理后通过原严格检查，定向编辑和内容/关系保持通过，并具备已登记受测特性的兼容证据。原始生成器基线继续失败，不因后处理通过而覆盖它。该机制不等待模型重复次数。
- 运行消费与错误收口（#23 线索）：检查消费者被占用、callback 首次拒绝和合法工具失败的生产边界。环境缺失、入口失效和实际准备失败正常收口只证明普通错误分类，不能证明事件消费停顿已经修复。首因来自真实拒绝诊断；历史首因未知与当前原生对话框阻塞分别结算。后者须有 owner 内修复或明确的 canonical SDK 依赖缺口，不能靠扩大队列、期限或平行消费者绕过。
- 样式处理与核验（#71 线索）：预先固定一个直接复现合计样式错位的坏文件、要求及独立 oracle，在一个真实模型 Task 中完成错误发现、修正副本、完整复验与真实交付。检查实际合计标签、完整字体/填充/百分比范围及普通行残留的错误强调，并核对原件保护、交付摘要和最终说明。模型或服务执行失败保留为该次未通过，不无限追加尝试。

原 F-XLSX 三次独立创建/修改、必要未支持场景、已配置第二模型对照，F-PPTX 三次模型工作流及独立 profile 首次准备，保留为后续稳定性评估。这些场景的输入和独立 oracle 不变，未完成部分继续标为未验收。DOCX 只回归本轮共享资源实际影响的既有路径。

定向模型验收使用已有可用且获授权的模型，记录实际选择并限定结论；不为测试新增 Provider、凭据或服务配置。下载和真实模型调用仍沿实际执行时已有的同意/授权边界进行，本计划本身不替代这些同意。

记录全部尝试、工具轨迹与最终结果，不只保留成功样本。必需场景中出现漏检、错误交付或“未检查却声称通过”，该轮工作流验收不通过；模型/服务运行失败记为失败或阻塞，也不能从统计中删去。调整实现后可对新输入身份复验，但前次结果仍保留。验收结果记录实际覆盖的模型、任务和文档类型，未覆盖部分明确列为待验证；新增用户场景和已支持场景中的失败持续补入回归，作为能力完善的依据。

## 11. 验证入口与平台选择

延用现有标准入口，并在实现时把文档质量行为与依赖组合资格接入正式 test graph。新增检查 suite 和参数由代码唯一声明，验证规范只维护其标准调用与责任，不在本计划维护另一份机器测试清单。

## 14. 风险与完成条件

主要风险及处理：

- XSD 合规与实际查看器行为存在差异：分开取证，备注相关决策等待真实兼容性结果，不以删除特性通过。
- 同一模型同时生成代码和检查说明，可能遗漏同一要求：提供可执行示例、明确覆盖范围，资格测试持有独立 oracle；测量真实模型遵循程度并如实限定保证。
- 新检查报告产生虚假权威：绑定字节和检查范围，但明确它不是 Host receipt；不改变 DeliverFile 的可信边界。
- 报告过期或检查期间文件变化：对同一受检副本计算摘要并检查身份；修改后重新检查，交付前复核候选。
- 依赖升级扩大平台影响：依照实际发行输入和原生差异选择验证，损坏正式目录仍保留并明确失败。
- 过度建设公共框架：首期只有受控检查族、共享 IO/报告语义及必要格式实现；不增加规则语言、插件 registry、后台服务、安装状态机或质量数据库。

专项整体完成须同时满足：

1. 运行链的合法失败、取消、重试和终态均通过正式路径回归；#23 的首因有证据支持的结论，历史摘要与当前修复范围明确区分。
2. #28 的结构问题在被接受的固定输入与生产流程上消失，必要兼容性证据齐备，严格检查没有被弱化。
3. #71 的数据清洗/汇总场景有独立数值、合计坐标、样式和百分比检查；故意破坏样本能够失败；§10.1 定向模型任务的错误发现、修正、复验和实际交付成立，缺少的检查没有被叙述为已执行，保证范围限定到实际受测输入。
4. 按各 issue 的实际失败模式选择最小充分回归，三格式共享变更仍须覆盖受影响的既有路径。XLSX 的定向修正须保留原件并比对检查报告与真实交付回执；PPTX 须完成新建、定向修改、严格结构及受测内容/关系保持。后续模型矩阵不作为本轮逐 issue 结算的前置条件，其未验收状态单独保留。
5. 机器确定性检查、真实 Core/Product 集成、模型工作流和查看器证据分别给出结果，必要平台缺口明确保留。
6. 资源、实现、测试、标准入口及对应真源一致，没有平行规则、全局环境 fallback、第三方本地 patch 或跳过 verifier 的路径。

issue 关闭应附根因、修复 owner、最小回归与证据范围。#23 不能以 Office 安装成功关闭，#28 不能以其他查看器可打开关闭，#71 不能以一次模型输出看起来正确关闭。若当前仍有未闭合项，可以交付已完成工作包，但专项和对应 issue 保持未完成结论。
