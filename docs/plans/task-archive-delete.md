# Task 直接删除与设置内归档管理方案

日期：2026-10-26。状态：已实施；关联验证通过，标准全量测试与格式检查仍有未闭合项，见[验收证据](../evidence/task-archive-macos-20261026.json)。

本文整理本次用户讨论，包括最后补充的归档成功提示。本文是实施计划，不是 decision record，不替代现有规范，方案正文保留讨论时的范围，实施与运行验证结论以文末状态及验收证据为准。实施时按仓库 AGENTS.md 更新对应真源；当前行为以代码与现行合同为准。

## 1. 产品语义与范围

| 动作 | 用户意图 | 产品结果 |
| --- | --- | --- |
| 归档 | 暂时不处理，以后可能继续 | 从日常导航隐藏，保留任务、历史和引用 |
| 恢复 | 重新关注任务 | 回到日常列表及原项目，继续使用原 Task |
| 删除 | 永久移除任务记录 | 删除任务历史及其专属内部资源，保留工作目录中的真实文件 |

删除取消“必须先归档”的条件。归档状态与删除进度独立，直接删除不暗中把普通任务改为归档任务，失败也保留原归档状态。Run 完成仍只表示该轮执行结果，不代表 Task 已归档。

本次包含直接删除、运行中的停止并删除、设置归档页、历史查看及返回、归档成功提示、失败恢复、跨语言状态合同和对应验证。不新增回收站、批量操作、归档自动清理、文件删除选项、历史数据库切换或第二套任务存储。

## 2. 日常导航与任务菜单

- 普通任务右键菜单为重命名、归档、删除；删除不再依赖 archived。
- 全局列表与项目列表始终隐藏归档任务，移除“显示已归档”开关及其状态和旧文案。计数按唯一可见 Task 计算。
- 归档要求没有 active operation。排队、运行、等待用户、停止、压缩或恢复期间归档不可用，说明“停止当前操作后可归档”；不新增“停止并归档”。
- 删除允许一次确认完成停止和删除。未结束的配置或审批事务仍须遵守各自互斥与未知结果边界，不能被删除绕过。
- 当前打开的任务归档后，左侧入口消失，但当前历史画面保留，并持续显示归档说明。用户无需因归档被强制切到新任务页。

## 3. 归档成功提示

Host 确认归档已生效后，显示非模态轻提示：

> 任务已归档，可在“设置 → 已归档任务”中查看。
>
> 撤销 · 查看

- “撤销”对该 Task identity 调用既有恢复动作，等待 Host 确认，不乐观翻转 archived。恢复失败显示准确反馈，不能假装已经撤销。
- “查看”直接打开设置中的“已归档任务”。
- 提示采用现有通知组件的定时规则；鼠标悬停或键盘焦点位于提示内时暂停自动消失。动作具备可访问名称，不抢走当前焦点。
- 提示按准确 Task identity 绑定；新提示不能把旧“撤销”目标重定向到当前选中任务。目标已删除或正在删除时不再允许撤销。
- 归档失败时保留原列表项，显示失败原因并允许显式重试。
- 命令超时先对账 Host 当前状态，不自动重发归档。确认 archived 后才能显示成功提示，不以超时本身推断成功或失败。
- 归档保存继续遵守现有 best-effort 历史持久化语义；保存健康异常沿既有提示呈现，不把内存生效表述成已可靠写盘。

如果归档的是当前查看的任务，轻提示消失后仍保留工作面内的“此任务已归档”说明、“恢复任务”和“返回已归档任务”入口。

## 4. 设置中的已归档任务

设置导航新增独立项“已归档任务”，与常规、账号、模型等现有分区平级，放在现有导航末尾。即使没有归档任务也保留入口。仍沿用完整 Settings surface，不重复显示或操作底层 Task 左栏。

页面使用紧凑列表：任务名称、所属位置、恢复和删除动作，以及必要的删除进度或失败说明。手动项目使用现有目录名称，自动工作区使用现有产品名称；不暴露内部 workspace key，不提供 Workspace 生命周期管理。

- 搜索按任务名称过滤，不在本次新增全文索引能力。
- 默认按现有 recentOrder 倒序，不标称“按归档时间”。
- 首版不显示归档时间：当前没有独立可信字段，不用其他时间推断，也不为此增加持久化迁移。
- 总数和行集合来自 Host canonical task index，项目重复入口不重复计数。不能沿用日常列表的 archived 过滤；目录当前不可用不等于应该删除已发布历史。
- 只管理当前 Host 能投影的记录，不扫描工作目录或原始 store 猜测任务。无法读取的历史沿既有 retained history 规则处理。
- 空状态显示“归档的任务会显示在这里”；搜索无结果显示“没有找到匹配的任务”。未加载和读取失败分别显示，不能伪装成空列表。
- 因版本未知字段恢复的 history_read_only 任务可以阅读，恢复、删除和其他修改继续禁用并解释原因。
- 删除中保留列表行和“正在删除”状态；失败保留原行与显式重试入口。

## 5. 历史查看、返回与恢复

点击归档任务名称，显式离开设置，进入现有 Task 工作面，复用已有对话、执行历史与详情，不在设置内维护第二套历史渲染或查询协议。

工作面持续显示：

> 此任务已归档。恢复后可以继续。
>
> 返回已归档任务 · 恢复任务

归档历史不提供可发送 Composer、改名、模型及审批模式编辑入口。归档导致的只读展示使用 archived 事实，不能写入或冒用表示版本兼容问题的 historyReadOnly。既有历史文件动作仍须逐次通过当前 Host authority 与内容校验，归档不授予额外读盘权限，也不保证当前文件与历史相同。

返回入口重新打开设置的归档列表，保留搜索条件、滚动位置和合理的焦点。目标行已消失时焦点回到相邻有效行或列表标题。其他任务及新任务草稿、阅读位置沿现有归属保留。

- 设置列表的“恢复”：确认后移出归档列表，留在设置，显示“任务已恢复”。
- 历史工作面的“恢复任务”：确认后留在该任务，恢复普通工作面。
- 两处使用同一 typed archive mutation，不复制 Task，不新建 Workspace，不自动发送消息或 Run。
- 恢复保留原 Task identity、历史和工作目录，沿现有 recentOrder 更新规则回到日常排序。
- 恢复只解除归档，不保证模型、目录授权或 Conversation 当前可执行；不满足时继续消费 Host gate 与说明。
- 归档确认当前完成提醒，恢复不复活旧提醒。
- 已有全局搜索命中归档任务时标明“已归档”，打开同一历史工作面，不自动恢复，不借此开放尚未接通的搜索能力。

## 6. 删除确认与 Host 推进

删除确认以 Task identity 固定目标，显示任务名称；之后切换选中任务不能更换删除对象。普通任务与归档任务使用同一删除用例。

确认文案：

> 删除任务“任务名称”？
>
> 任务及其对话、执行历史将被永久删除。工作目录中的文件会保留。
> 如任务正在运行，将先停止运行。

默认焦点为“取消”。危险按钮在无运行时显示“删除任务”，有运行时显示“停止并删除”。确认框未提交前不产生停止或删除副作用。

Renderer 只提交一次现有删除命令；Host 负责以下完整过程，不能由前端串联 cancel、等待和 delete：

1. 在同一 Task 事务中接受删除意图并发布 deleting，立即拒绝新输入、新 Run 和冲突修改；不改变 archived。
2. 取消尚未采用的等待输入与接续，使待决审批和迟到结果失去生效资格，不重放工具或历史输入。
3. 沿原 owner 路径请求停止当前 operation，等待真实 terminal 和事件 drain。
4. 等待 Session、checkpoint、callback、worker reference、执行记录及其他相关资源静止，不把取消受理当作静止证据。
5. 确认 durable history 已移除 Task 后，才物理释放记录与其专属内部资源。Automatic Workspace record 的释放仍遵守现有条件；真实目录不递归删除。

deleting 期间禁用重命名、归档、恢复、发送和重复删除，允许导航离开。列表行保留在原位置并显示进度，Host 独立于 Renderer 持续推进，不要求用户反复提交。命令 ACK 只说明受理；Task 确实被移除后才显示成功和移除列表行。

删除当前 Task 成功后回到新任务页，保留已有的新任务草稿，不自动选择另一个 Task。删除其他 Task 不改变当前工作面。停止期间已经形成的文件修改不回滚，不能把删除解释成撤销文件操作。

## 7. 删除失败、结果未知与重启

继续使用 runtime-only deletionStatus = idle | deleting | failed，不增加 Task 产品终态或 durable deletion intent。

| 情况 | 行为 |
| --- | --- |
| 普通任务删除失败，Host 确认 open 且后续操作安全 | 保留普通任务及失败信号，允许重试删除，也可显式继续或归档 |
| 归档任务删除失败，Host 确认 open | 保留归档任务，允许重试删除或恢复归档 |
| 仍为 closing 或相关事务结果未知 | 可以阅读；按现有 gate 提供删除重试或恢复处理，不能开放不安全的继续/恢复 |
| 删除持久化明确失败 | 不释放 Task 和恢复所需资源，显示失败，不自动重试 |
| 删除提交结果未知 | 保留记录及必要资源，沿既有 history health/recovery 处理，不能猜测成功或无条件清理 |

普通任务失败后显式发送新消息或归档，表示放弃这次失败删除；Host 只有在重新确认安全且成功接纳新操作的同一次 mutation 中才清除 failed。操作未被接纳不清除失败。恢复归档也沿用同一原子清除原则。已停止 Run 不复活，新发送只能形成新的执行意图。

命令超时先刷新 canonical projection，不自动重发；只有明确且安全的显式重试才推进下一次删除。其他 Task 和整个 Workbench 不因单项失败冻结。

重启不自动恢复未完成的删除意图。任务记录仍存在时按原 archived 恢复；已经确认提交的删除不再出现；既有恢复规则收口进程退出时的 non-terminal Run，不重放执行。不能根据旧 UI 的“正在删除”推断 store 结果。

## 8. 实现与真源职责

复用现有 metawork.tasks.archive 与 metawork.tasks.delete 命令、Task identity、archived 和 deletionStatus，不新增归档数据库、平行 active path 或宽泛 facade。移除专属 TaskNotArchived 拒绝及过时断言时，同步替换为新业务规则和严格验证。

| 范围 | 实施职责 |
| --- | --- |
| Task Runtime / Product Control | 直接删除 admission、停止并删除、消息与审批失效、失败后的安全继续、commit-before-release |
| Host serializer / Renderer decoder / fixture | 接受未归档 Task 的 deleting/failed；保留 deleting 必须 closing 及 active operation、continuation、只读历史的一致性校验 |
| TaskList / selectors | 移除 showArchived 状态和开关，日常列表与计数一致过滤归档，普通 Task 删除入口可用 |
| Settings | 已归档任务列表、搜索、空/错/进度状态、恢复和删除 |
| App / shared feedback | 固定操作目标、归档 toast、撤销/查看、历史返回路径、焦点和删除完成后的导航 |

归档列表可独立为展示组件；命令和 pending 状态继续由既有 App/Host owner 管理。底层 Task、草稿及权限不复制到设置中的第二份 authority。

## 9. 实施顺序

1. 更新对应合同和跨语言 fixture，明确 accepted deletion 不要求 archived、deleting 对应 closing，以及失败后的安全 admission。
2. 实现 Host 完整删除推进及失败恢复，验证有活动 operation 时的资源屏障。
3. 接入普通 Task 删除、设置归档管理、归档 toast 与历史返回导航。
4. 删除旧 showArchived 路径、归档前置拒绝和对应过时测试，不保留平行实现。
5. 完成关联回归与当前平台真实 desktop vertical；只有证据通过后才标记实施完成。

## 10. 验证与验收

- Renderer：typecheck；TaskList、设置、归档可见性、删除确认和 pending、toast、导航、焦点、搜索及中英文受影响 suite。
- Task Runtime：普通 Task 直接删除且 archived 不变；各类 active operation 的停止、等待消息取消、审批失效、迟到结果、幂等受理、失败后显式新意图原子清除失败。
- Product lifecycle：Run/compact/restore、真实 Session 收口、event drain、checkpoint 与 worker lease、history commit 明确失败和 outcome unknown、不释放 live reference、shutdown/重启不重放。
- Bridge：Host 与 Renderer 两侧 fixture、TaskSummary/TaskView/scoped projection 的新合法组合和仍须拒绝的畸形组合。不得只删旧拒绝测试而没有替代断言。
- 具体定向入口沿用 zig build test-product-task-runtime、zig build test-lifecycle、test-product-views 与现有 Node suites；标准收尾执行 npm run check 和 npm test，覆盖 canonical staged bundle verifier、Renderer 类型及正式 Native test graph。
- 当前 macOS 平台真实 Application → Bridge → Product → AgentCore 验证直接删除、停止并删除、归档 toast/撤销/查看、设置恢复、失败反馈及冷启动；补齐桌面、窄窗、键盘和焦点观察。
- 验证工作目录中文件在删除前后保持；对用户原有草稿、其他 Task 和正在运行的无关任务不产生副作用。
- bundle 缺失或 verifier 拒绝必须明确失败；逻辑测试不能冒充真实桌面证据，未执行的其他平台验收单独记录，不机械扩大平台矩阵。

## 11. 三轮复盘结论

| 复盘范围 | 为什么 | 最终取舍 |
| --- | --- | --- |
| 产品语义 | 删除为什么要经过归档 | 没有必要，取消该前置条件 |
| 产品语义 | 删除失败为什么要把普通任务转成归档 | 会改变用户意图，保留原状态 |
| 操作体验 | 为什么放设置、移除左栏开关 | 集中低频历史管理，简化日常导航 |
| 操作体验 | 为什么归档后还要提示 | 入口迁移后必须解释任务去了哪里，并提供撤销和直达 |
| 操作体验 | 为什么当前历史还要持续提示 | toast 会消失，工作面需要继续解释不能发送及如何恢复 |
| 操作体验 | 为什么复用现有历史工作面 | 保持消息、工具详情和文件访问行为一致，避免第二套 renderer |
| 数据范围 | 为什么没有归档时间 | 当前无可信字段，不伪造，不为展示增加格式迁移 |
| 生命周期 | 为什么由 Host 停止并删除 | 导航、断连和迟到回调不能打断或重复执行事务 |
| 生命周期 | 为什么不收到 ACK 就移除任务 | 后续停止、释放或提交仍可能失败 |
| 生命周期 | 为什么重启后不自动继续删除 | 删除意图未持久化，不从瞬态 UI 推断或重放破坏性意图 |
| 范围控制 | 为什么不顺便加回收站 | 涉及独立的保留、清理和恢复合同，当前没有请求 |

实现、规范合同和关联验证已完成。正式 Native graph 与当前 macOS 的真实 Host/界面路径通过；完整 Node 集存在定时任务选择时序与 TaskPanel 异常退出，仓库级格式检查存在未改动 TaskContent.tsx 的既有格式问题，不宣称全部检查全绿。详细命令、身份、范围和未闭合项由验收证据拥有。
