# MetaWork Office 扩展实施方案

MetaWork 将 Office 文档处理作为用户可选安装的官方扩展能力。主包保持轻量，只提供组件管理、成果交付和预览控制；完整 Skill 资源、解释器、文档库与转换引擎独立下载。普通使用不下载 Office 重依赖，用户主动启用后可离线处理文档。

本文是 2026 年 10 月 22 日收敛的待实施计划，不是 decision record，也不替代现行规范。本文中的新增能力、协议和分发方式均须在实施及验收后，按领域更新对应真源；当前代码和发布能力不因本文建立而改变。

## 1 目标与范围

首版打通以下流程：用户启用 Office 组件，提交文件或创建需求，Agent 通过 Skill 处理工作副本，完成检查并明确交付，用户在产品内预览、另存和继续修改。

| 范围     | 首版要求                                                   |
| -------- | ---------------------------------------------------------- |
| 文档格式 | DOCX、XLSX、PPTX 的读取、创建和修改                        |
| Word     | 包含接受修订及结果检查，不要求保留现有宏实现               |
| Excel    | 包含公式保留、实际重算和结果检查                           |
| 转换     | 页面渲染和 PDF 导出；PDF 页面预览按同一引擎的实际支持验收  |
| 成果     | 明确登记，核验文件身份，支持预览、另存、定位和继续修改     |
| 预览     | Host 准备分页图片或有界只读网格，Renderer 展示             |
| 分发     | 轻量主包，一个按目标平台发布、由用户主动安装的 Office 组件 |

旧 Office 二进制格式、用户文档宏、加密文件和复杂版式完全保真不扩大为首版承诺。现有 `.doc` 等指引须与实际支持一致。完整 Office 编辑器、人机双写、PDF.js 查看器、历史成果副本仓库、通用扩展平台和引擎自动 fallback 不进入本次范围。

本方案不以新增 AgentCore ABI、独立 AgentCore Worker 或修改仓库执行政策为前提。Native SDK 的消费边界继续遵守[高层架构](../architecture.md#35-native-sdk)。

## 2 主包与组件

| 内容                                                    | 归属                     |
| ------------------------------------------------------- | ------------------------ |
| Office 支持范围、组件状态、安装入口、可信发布信息       | 主包                     |
| 组件下载、校验、解包、启用、取消和清理逻辑              | 主包                     |
| 三个格式 Skill 的完整指引、脚本、校验 schema 和必要资源 | Office 组件              |
| 必要的 Python、Node、文档库和唯一转换引擎               | Office 组件              |
| 成果记录、文件操作、预览协议和展示组件                  | 主包                     |
| 转换中间结果、页面图片、表格数据                        | 预览会话内的有界临时资源 |

首版只做一个 Office 组件，不把每个库做成独立下载项。组件未安装时，不向 Skill catalog 注册假装可执行的占位 Skill；安装入口与 Skill catalog 分离。附件仍可接收、保存，普通 Task 不因 Office 组件缺席而失去准入。

组件包含哪些依赖，由“用户行为—Skill 指引—工具入口—发布资源”对应表唯一追踪。现有开发环境不能直接整体搬入发布物。移除或替换 Pandoc、Poppler、MarkItDown 等入口时，必须同时收口对应指引并验证等价行为；保留的入口必须随组件可用。

运行时路径由 Host 验证并通过受支持的资源机制提供，正式内置工作流不依赖用户 PATH、全局包或系统 Office。开发态使用相同的组件布局与验证机制，逐步移除旧的专用环境拼接路径；现有用户自定义 Skill 和环境选择不因此被全局接管。

## 3 职责与执行路径

| 层              | 职责                                                                     |
| --------------- | ------------------------------------------------------------------------ |
| Skill           | 选择格式工作方法，按需加载指引，组织读取、修改、检查、修复和交付         |
| Office 工具资源 | 执行确定的读取检查、转换、渲染和重算，报告可观察结果                     |
| Product Control | 拥有组件管理事实、准入、配额及事务；Task 拥有成果事实和预览授权          |
| Application     | 执行下载、平台验证与进程 effect，管理产品预览启动的进程和资源生命周期    |
| Agent           | 消费 AgentCore Skill、Shell 和必要的窄 Host tool，交付可信执行回执       |
| Bridge          | 严格解码组件管理、成果和预览操作，运输 canonical projection 和受授权内容 |
| Renderer        | 展示状态、预览和成果，接收用户操作，不取得任意路径或进程 authority       |

这些职责放在现有 owner 内，不新增顶层 Office owner、常驻 Node 服务或通用环境管理平台。组件的机械文件检查不复制 Skill parser；来源、policy、winner/conflict 和 Task binding 继续沿用[Product 架构](../product-architecture.md#24-skill-authority-与本地资产)和[AgentCore 集成契约](../agentcore-integration.md#skill-catalog-ownership)。

文档处理沿既有 AgentCore Skill 与 Shell 路径执行。用户点击预览、另存和定位时，由产品直接处理，不启动模型。组件安装成功不能重放旧工具、历史输入或失败的副作用，也不能热替换正在使用的 Session catalog。

## 4 组件下载与安装

### 4.1 用户操作与发布身份

用户主动启用 Office 支持。安装前展示目标平台的下载量、安装后占用和用途；普通启动不静默下载。组件状态区分当前可用版本和安装操作进度，更新失败不把仍完好的当前版本标为损坏。

主包的唯一机器发布输入固定组件身份、目标平台、兼容要求、可信下载来源与摘要。正式安装不消费可变 `latest`，不接受模型或文档给出的下载 URL。远端清单不能独立扩大主包信任的组件集合。

组件内引擎或解释器出安全修复时，需要发布包含新组件信任信息的主包版本；这一代价须进入平台分发真源。更新主包不意味着无条件下载组件，未启用 Office 的用户继续不下载。

### 4.2 安装事务

安装采用单一事务路径：

1. 检查目标平台、磁盘容量、预期组件身份和当前安装操作。
2. 下载到独立 staging 文件，执行期限、大小和取消约束。
3. 校验主包固定的发布身份与摘要。
4. 在新 staging 目录中有界解包，检查目录清单与必要资源。
5. 验证目标平台、解释器、库、引擎、签名和最小自检行为。
6. 原子发布不可变版本目录，再提交当前可用组件事实。

下载、解包、校验或自检失败时，不能启用半成品或退回系统环境；旧的完好版本不被覆盖。取消须等文件句柄和子进程静止后清理。崩溃残留在后续安装或启动时辨认并收口，不作为成功资源复用。

安装、取消、修复和移除使用 typed 产品操作；进度与安全错误通过 canonical projection 呈现。组件准备不交给 Agent 执行 `pip install`、`npm install`，不静默提权或安装全局环境。

### 4.3 归档格式与 bootstrap

首版采用固定的 `tar.gz` 组件归档，由主包可用的标准库或已批准能力解包。安装不能依赖尚未安装的组件内 Python；优先复用成熟实现，不因此自研通用归档库，也不调用不受控的系统解包程序。

组件归档与普通用户 ZIP 使用不同的接受合同。普通附件 helper 的拒绝链接规则保持不变；组件归档按受信任发布格式处理必要链接，并满足：

- 压缩量、展开量、成员数、metadata、路径长度和深度均有明确上限，实际写出量计数；
- 拒绝绝对路径、路径越界、碰撞、特殊文件和不需要的硬链接；
- 只有发布物实际需要时才允许相对符号链接，解析后的目标须始终处于组件根内，拒绝循环、链式逃逸和通过链接父目录写出；
- 保留必要可执行位，忽略归档 owner 和特殊权限位，按平台限定允许的权限；
- macOS 签名封印所需的目录、链接和资源结构须完整保留，并在安装自检中执行 `codesign --verify` 等对应验证；
- Windows 可执行产物的签名、体系结构和运行库要求进入安装验证及干净机器验收。

归档格式、清单和发布身份在实际消费前写入分发合同；容量值以目标平台产物测量确定，由机器输入拥有，不能把用户 ZIP 的默认预算直接照搬给组件。

## 5 版本持有与清理

不在 Task/Session 持久化 Office 组件版本，不建立历史 Task 对旧运行时的跨重启引用。组件安装记录可以持久保存当前组件身份和安装事务状态，但不成为 Task 历史的一部分。

只跟踪进程内引用：catalog query、catalog lease、捕获的同进程恢复输入、正在执行的进程、安装自检以及预览 handle。新版本安装到独立目录；新 Task 和显式 idle refresh 使用当前版本，已有 Session 保持原 lease，刷新失败保留原输入。

冷恢复遵守现有空 Skill authority 合同，恢复后再显式准备当前可用 catalog。同进程切换仍保留 captured 输入，不能借组件更新扩大 authority。旧对话中的旧绝对工具路径在目录清理后可以如实失败，不创建兼容软链接、不重写 checkpoint，也不因这些文本永久保留组件。

旧版本标记待清理，无进程内引用后删除。仍被引用时显示待清理，必要时提示“重启后完成”；下次启动在取得相应目录使用权后清理。活动运行期间不覆盖或删除版本目录。

实施前核对实际产物的 identity、数据目录和单实例规则，不能预设正式 release 与 dev 已共用目录，也不为本任务迁移现有业务数据。组件存储限定在明确的产品 namespace 内，不建立全局共享运行时仓库。若不同构建实际共用存储，复用现有互斥能力证明清理不会影响另一实例；无法证明时保留并报告待清理。离线构建后续可能需要重新安装其固定组件，文案须说明，但文案不能代替正确的资源保护。

## 6 行为验收与唯一引擎

引擎选型以用户行为为准，不以现有命令名为保留目标。LibreOffice Kit 是候选；在行为、平台产物、维护与发布稳定性验证前不预设采用。

| 行为                      | 验收要求                                                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| DOCX/XLSX/PPTX 读取与修改 | 内容范围正确，修改目标完成，相关结构未误改，结果可重新打开                               |
| 接受 Word 修订            | 实际接受修订，验证段落、表格、格式等代表性样本；不以进程退出码或简单删除标签代替语义验证 |
| Excel 重算                | 相关公式保留，引用正确，缓存结果实际更新，公式错误或缺失结果可解释                       |
| 渲染与导出                | 页面与内容完整、中文可读；字体替换、分页、图表与图片按支持范围检查                       |
| 生命周期                  | 超时、取消、外层强杀、并发、临时目录和失败输出清理均有真实观察                           |
| 发布                      | 目标平台、离线运行、特殊路径、签名后的安装位置和干净机器通过                             |

候选不能满足接受修订等既定行为时，默认结果是候选落选。削减能力须明确变更范围，不留下完整 soffice 单独跑某项工作流，不做转换失败后的第二引擎 fallback。

唯一引擎限定转换、渲染和重算；格式创作库可以不同。只打包实际使用的依赖，删去已替换的入口与指引；不为消除一个解释器而未经行为验收重写成熟工作流。

## 7 Skill 与执行可靠性

保留 `docx`、`xlsx`、`pptx` 三个入口。入口说明用途、方法选择、受验证的工具入口和交付要求，详细编辑、渲染、重算、导出指引按需读取。共用工具不自动成为额外 Skill。

先完成引擎无关的修复：

- 全部 OOXML 读取路径纳入有界预检，包括解包、校验器、读取原件和直接读取 ZIP 内 XML 的 helper；单个成员读取也限制实际解压量；
- 第三方库消费经过检查的同一份工作副本，不能只保护显式 unpack 入口；
- 原件缺失、输入输出身份冲突明确失败，编辑采用工作副本；
- 临时结果检查成功后才发布，失败不留下看似完成的目标文件；
- 接受修订、公式保留、重新打开和输出内容都有后置检查。

选定引擎后，再一次性统一转换入口、profile、临时目录、期限、捕获预算和取消，避免在旧引擎上修完又重写。

| 调用路径          | 生命周期责任                                                     |
| ----------------- | ---------------------------------------------------------------- |
| 产品预览          | Application 管理自己启动的转换进程，Product 决定准入和资源持有   |
| 模型经 Shell 执行 | AgentCore Shell 负责外层执行；文档执行入口负责其启动的转换子进程 |

外层 Python/Node 被强杀属于必须验证的失败模式。`subprocess.run(timeout)`、进程组或 `finally` 均不能单独证明整棵进程树已退出；先实测所选引擎和当前 Shell，再确定满足目标平台的最小机制。涉及原生 effect 时遵守 SDK 边界，不新建通用进程框架，也不把局部约束描述成任意 Bash 的完整沙箱。

检查强度随任务变化：内容提取检查读取范围；内容修改检查目标与结构；公式修改检查实际重算；外观修改检查受影响页面或区域。模型无法看图时，区分结构检查完成和视觉检查未完成，不能声称排版已验收。

## 8 最小成果交付

增加明确的成果交付动作，`DeliverFile` 仅是方案中的示意名称，正式工具与 wire 名在合同设计时确定。该动作不生成或转换文档；Host 校验 Task、Run、Workspace authority、普通文件身份和容量后，登记成果。

成果记录只保存 Task/Run 身份、受授权 locator、交付时的内容摘要和大小，以及必要的安全展示信息。首版不保存历史成果字节副本。

| 对象           | 含义                                           |
| -------------- | ---------------------------------------------- |
| File Reference | Run 引用了哪个文件                             |
| Files Changed  | 观察到哪些文件副作用                           |
| Output         | Agent 或用户明确选择交付、且经 Host 验证的成果 |

不从 stdout JSON、Markdown 链接、新建文件或文件后缀推断 Output。可借鉴已有 Host tool 回执模式，但须定义窄合同和线性提交点；不伪造 Core event，也不让回调持有 Product 内部指针。Host 证明文件身份，不把模型自述当作质量验证凭据。

成果支持预览、另存、定位 Workspace 源文件和继续修改。使用时重新验证摘要：已变化显示“交付后已变更”，缺失或授权失效明确不可用。另存从同一份稳定读取中复制并验证实际字节，检查成功后发布目标；不能只在复制前检查一次源文件。

定位通过 Application 消费 Native SDK 正式能力，不借 `external_link_handoff` 传递 `file://`。同一 Task 内继续修改可使用正常文件引用；跨 Task 导入和外部文件接入按对应输入授权处理，不要求所有成果重新走附件 staging。

新增成果记录按 Storage 迁移规则接入，保留现有附件路径和持久数据。历史附件 chip 的预览定位另需明确的 Host 映射，不能靠名称或解析 checkpoint 补猜，不作为首版成果能力的前提。

## 9 文档预览

### 9.1 页面与表格

DOCX/PPTX 由 Host 准备可复用中间结果并按需生成页面图片；PDF 页面渲染使用选定引擎的经验证能力。复用现有图片运输和展示组件，不在主 WebView 解析 PDF。首版接受不能选择页面文本的限制。

XLSX 由组件运行时解析，Renderer 只接收有界、按需的 typed 只读网格数据。支持工作表、单元格选择、公式和已保存结果的区分及常见格式；预览不触发重算。缺失公式缓存与未显示的重要对象须可解释；图表、打印布局等检查使用同一引擎的页面渲染。具体网格投影和支持范围须先定义，不能增加完整编辑或公式引擎作为隐含前提。

### 9.2 会话与 wire

文档预览新增 typed 会话操作，不能直接给现有五字段 `metawork.files.preview` 请求添加页码，也不能将 PDF 伪装为 image。复用的是已有运输原语与资源约束，文档会话和分页本身属于新 wire。

| 操作 | 含义                                                                                     |
| ---- | ---------------------------------------------------------------------------------------- |
| 打开 | 校验 Task/Run 文件引用或成果身份，准备文档，返回 opaque handle、源版本、页数或工作表概要 |
| 读取 | 以 handle 请求指定页或有界表格区域；不提交文件路径                                       |
| 刷新 | 重新核验目标并建立新一代预览，拒绝旧异步结果                                             |
| 释放 | 撤销 handle、取消在途操作，并在物理资源静止后完成清理                                    |

handle 绑定 connection/window、Task、目标和 generation；它不取代每次读取的授权校验。现有文本和普通图片预览保持语义，新协议按[Bridge 合同](../renderer-bridge-contract.md#file-preview-command)演进并同步跨语言类型与 fixture。正式字段、容量和状态枚举在该阶段设计并验收，不在此预造第二份协议定义。

### 9.3 暂存与调度

Product Control 拥有预览资源，Application 管理转换进程；标签只决定使用期限，不成为 Host owner。允许预览会话内有界暂存和必要的私有临时文件，不做跨 Task、跨重启的持久预览缓存。

文档一次准备中间结果，翻页不重复整份布局转换；工作簿一次解析，区域请求不反复启动 Python 重载整本文件。预览身份包含源内容、引擎、选项、字体环境、授权和安全代次。每次读取核验源版本，刷新重新准备，不增加文件 watcher。

关闭、Task/引用失效、断连、安全代次变化、期限到达、组件移除和 shutdown 均须撤销并释放。隐藏标签按现有交互保留状态，但临时资源总量有界；资源失效后不得显示旧内容或接受迟到响应。

转换使用独立有界 lane，首版一个活动转换和少量排队即可，不占用现有 File Preview worker。重解析、转换和大内容准备不在主线程进行。逻辑配额不等同于进程内存隔离，验收必须观察实际 CPU、内存、延迟和取消行为。

### 9.4 内容与凭据边界

在发布新预览内容前，定义已知系统 credential 对 Office/PDF 文本提取、结构化投影和转换内容的检查范围、命中拒绝策略及无法检查时的行为。不以扫描栅格图片或压缩文件原字节代替正文检查，不修改用户原件来伪造脱敏成功。

检查覆盖当前产品承诺的系统 credential 防泄漏边界，不承诺识别用户文档中的所有秘密，也不扩展为通用 OCR/DLP 项目。宏、外部链接加载和嵌入内容的接受规则须随引擎验收明确，不把引擎可读取等同于产品可开放。

## 10 轻量与分发验收

| 指标     | 要求                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------- |
| 主包     | 按平台以当前可重复构建的签名/分发产物建立基线和明确增量预算，超限构建失败；单独检查重依赖未混入 |
| 首次下载 | 展示对应平台组件的实际下载量，不用源码目录大小估算                                              |
| 安装占用 | 测量运行时、安装峰值、临时结果和待清理版本，提供清理反馈                                        |
| 更新成本 | 相同组件身份复用，主包更新不强制重下未变化组件；仅保留有进程内引用的待清理旧版本                |
| 干净机器 | 不依赖全局解释器、开发 PATH 或预装 Office；验证 Windows CRT、macOS 签名、中文字体和离线工作流   |

精确预算、组件版本、摘要与平台资源清单由唯一机器输入拥有。不同平台分别记录，不能把单个 executable 大小当作完整安装包体积。引擎、解释器或依赖更新后重新验证受影响的平台产物，不继承不匹配身份的旧证据。

## 11 实施顺序与完成标准

| 阶段             | 工作内容                                                                 | 完成标准                                                                                              |
| ---------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 1 范围与基础修复 | 行为与依赖对应表；归档读取、工作副本和后置检查；建立主包体积基线         | 所有保留指引都有对应入口，失败模式有最小回归，转换相关实现尚未重复改写                                |
| 2 引擎与组件     | 比较并选定唯一引擎；统一转换生命周期；构建、下载、解包、验证、启用和清理 | 干净机器主动安装后离线完成 DOCX 纵向链路，再接入 XLSX/PPTX；取消、外层强杀、版本 lease 和体积检查通过 |
| 3 成果交付       | 明确交付动作、Host 回执、最小记录、另存与定位                            | 身份可信，源文件变化可识别，复制校验同一字节；无历史副本仓库                                          |
| 4 文档预览       | wire、预览会话、独立 lane、分页图片和只读网格                            | 不调用模型、不每页重转、不阻塞普通预览，credential 边界和资源释放验证通过                             |
| 5 综合验收       | 真实 Core、真实模型、平台安装与升级清理                                  | 机制、模型任务质量、平台行为和体积证据分别闭合                                                        |

第 2 阶段开始前必须固定组件归档格式与 bootstrap 方式、行为验收清单、仅进程内版本引用政策，以及真实 namespace/互斥策略。第 4 阶段开始前必须确定 wire、暂存失效规则、调度预算和 credential 检查语义；这些是该阶段的进入条件，不以现有图片链路可用代替。

验证分层执行：

- 确定性回归覆盖归档预算、链接、原件字节、公式保留、修订处理、失败输出、事务中断和取消；
- 当前 canonical AgentCore 的 vertical 覆盖 Skill 发现、权限、资源展开、真实执行、成果登记、冷恢复后的显式准备和删除；
- 真实模型任务验证自然语言请求能选对方法并完成 Word、Excel、PPT 工作，不能用脚本 Provider 替代；
- 平台专项覆盖签名、安装位置、运行库、进程退出、文件锁、字体、离线及升级清理；共享逻辑不机械重复扩大平台矩阵。

缺少 canonical bundle、组件或平台环境时明确报告未验证，不跳过后宣称成功。现有测试通过仅证明其观测范围，不证明新组件、引擎或模型任务质量。
