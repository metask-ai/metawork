# MetaWork Product 内部架构

> 状态：Product owner、事务、并发、恢复及其与 Agent 执行边界协作的当前规范
> 日期：2026-08-08

Task history 当前采用 hard-cut `workbench-history.store` record store：旧 JSON envelope 不读取、不迁移、不双写；Workspace/Task frame 独立校验，单条损坏只进入 `degraded`，不阻塞有效历史或新 Task admission。

顶层模块、进程方向和跨模块安全边界见 [MetaWork 高层架构](architecture.md)。本文件定义 Product 内部的 `account`、`workbench` owner、它们与相邻 Agent 执行边界的产品协作，以及由 Application 负责的跨 owner 协调和生命周期顺序；实际目录和依赖见 [工程结构与所有权](project-structure.md)，AgentCore 线程与 ABI 生命周期见 [AgentCore 集成契约](agentcore-integration.md)，Metask Account 外部合同见 [Metask Account API 合同](metask-account-contract.md)。

## 1. 模块与 owner

Product 内部由两个 named product owners 组成；跨 owner 用例由 Application coordinator 编排：

- `account` 的 Runtime 负责 Metask 登录、catalog、credential、attempt/effect/mailbox、恢复与 ExecutionConfig generation；
- `workbench` 拥有产品状态、Task、队列、投影与持久化语义，并直接消费相邻 Agent 的公共执行能力。

Agent 是 Product 之外的 MetaWork-owned 执行边界，也是 AgentCore integration owner，拥有 MetaWork 对 AgentCore Runtime、Session、Conversation 的集成生命周期、callback、event pump 与 terminal execution facts。Application 创建并关闭 Agent、安排 event-ready 主线程 wake；Workbench 直接调用 Agent，但不管理 Agent Runtime 生命周期、不读取 Runtime 内部字段，也不借 Agent 获取通用 I/O。

Application coordinator 负责 Account/Workbench 主线程跨 owner 提交与全局生命周期顺序，不持有领域运行状态，也不独立决定 Account、Workbench 或 Agent policy。它由 `src/app/` 下的具名 coordinator 实现，`app.zig` 只负责装配；这不产生新的产品 owner。Bridge 位于 Product 之外；`metawork_account_contract` 只承载 Account 发布给 Application/Bridge/Workbench 的有界纯合同。Application、Agent、Renderer 与原生窗口边界只由 [高层架构](architecture.md)定义。

Product 内部负责：

- 由 Account 在 Renderer 之外完成 Metask OAuth、目录查询、凭据持久化与 ExecutionConfig 生成；
- 由 Account Runtime 在 committed transition 之后产生有界 continuation，由 Application coordinator 将其重新送入同一提交链；登录后的确定性目录准备留在后台，并只把真实歧义投影成用户动作；
- 由 Application coordinator 在同一主线程 turn 内协调 Account prepare、Workbench no-fail install 和 Account commit；
- 由 Workbench 管理持久 Scheduled Task、触发游标、有界 occurrence history、Task、Run/maintenance record、唯一 active operation 槽、队列、取消协调和产品历史；
- 由 Workbench 调用相邻 Agent 管理的 AgentCore Session、active Run/manual compact、callback binding 和有界事件泵，在主线程泵出 Agent event，并由 Product Task state 将事件应用为产品事实；
- 管理跨会话产品状态，并向 Bridge 提供 canonical 产品 projection。

Application 只向上述 Product owner 与相邻 Agent 注入其职责所需的能力：

- 在 `<MetaWork data dir>/workbench` 打开并持有 Task history 的进程级单写锁，把 bounded load/atomic replace capability 注入 Workbench；codec、恢复校验、candidate commit、持久化 health 和所有 Workspace/Task 产品事实仍归 Workbench；
- 通过 Native SDK `.data` 规则解析并打开 `<MetaWork data dir>/workspaces`，只把可用或不可用的 automatic root capability 注入 Workbench；由 Workbench 独占目录分配、Workspace 注册、Task 创建事务与回滚；
- 向 Workbench 注入原子 schedule persistence、wall clock、单一 Native timer、系统通知与后台窗口生命周期 capability；timer callback 只唤醒 Workbench due reconciliation，不直接调用 AgentCore。

MCP 仍服从上述边界：Workbench 通过其持有的 `product/mcp/configuration.zig` 子模块独占 `<MetaWork data dir>/mcp/registry.json` schema 2 的严格 codec、schema 1 hard migration、单 writer lock、原子替换、Desired Registry、由 Add/Replace 绑定的 connection approval、独立 OAuth consent、credential locator、`oauth_operation`、窄事务恢复与显式 tool allowlist；`product/mcp/state.zig` 持有当前 Runtime 对应的 immutable Runtime Manifest、Admission Authority、OAuth challenge scope、连接测试和完整 freshness 内存状态；`product/mcp/policy.zig` 纯化 authorization phase、pending reauthorization、Admission allowlist、refresh binding、generation gate、expiry/operation/recovery query 与 Admission 状态转换；`product/mcp/view.zig` 无状态地派生 management health、availability、runtime status、authorization/new-task access、connection/tool projection 与 redaction fact，并保持 Renderer Bridge revision 1 的 MCP snapshot 字节合同。`product/mcp/ports.zig` 定义不暴露 Workbench、具体 Executor 或 Agent Runtime 身份的窄 effects；`product/mcp/refresh_job.zig` 独占 worker payload、execute/cancel callback、atomic state 和 outcome，异步线程只写 job 自身，主线程仍按 request generation 安装完成结果。源码归入 `product/mcp` 不增加新的 Product owner，registry generation 也只作为 desired commit identity 与 optimistic concurrency。state 与 policy 可以消费 Agent 公共 Activation/Selection/allowlist 类型但不得消费 AgentCore SDK；policy 不持有 Agent Runtime，view 只依赖 configuration/state，敏感文本判断与 JSON 遮蔽通过 Workbench callback-scoped 借用完成；具体 durable commit、refresh job pointer、enqueue/cancel/commit、timer、revision publication、完整 snapshot 编排与交付仍由 Workbench 持有。Agent 继续拥有 stdio/Streamable HTTP connector/backend 生命周期、descriptor、official catalog/selection、Activation 与 typed health；Application 只注入 child/network mechanics，并拥有 secure secret capture、系统 credential、OAuth effect、earliest-expiry timer、Runtime HTTP auth snapshot，以及单一短寿命候选 Runtime 测试的编排。候选 Runtime 不进入正式 Manifest、Admission 或 Task 路径。Account 与 MCP 没有 ownership、credential service 或 persistence 依赖；Bridge 只运输 typed field intent 和安全 projection，不参与配置、授权、激活或 authority 事务。

MCP management coordinator 只编排上述既有 owner：Add/Replace 由 Workbench 在单次 transaction 中绑定完整 typed connection 与 approval fingerprint；legacy unapproved 配置仍可经窄 Host approval port 收口。明确保存后 coordinator 从 canonical desired 重新 preparation，构造完整 `McpRuntimeInput` 与 Runtime Manifest candidate，调用 Agent-owned declarative Runtime apply，再执行 official activation/catalog discovery；完成回到主线程后原子安装 Manifest、Activation、HTTP authorization owners 与 Admission Authority。`configuration_apply_job`、OAuth worker 与单一候选测试 worker 都是短期执行资源，不是第二份 registry、journal 或产品状态。`testConnection` 仍只构造隔离候选 Runtime并更新短期诊断，不替换正式 Runtime。shutdown 必须 join apply/test/OAuth worker 后再释放 owner。

Runtime Manifest 的 `loaded` entry 保存当前 Runtime 已完整接管的 descriptor fingerprint，`absent` entry 保存 disabled、structurally invalid、missing authentication 或 credential-invalid 等无 secret absence proof；成功接管空 input 形成零 entry Manifest。compatibility 关系仍派生 `current | restart_required | unknown`，但 `restart_required` 现在表示正式 apply 尚未完成，不是用户必须重启 Application。Workbench 在 apply 开始时安装 `blocked(refreshing)`；AgentCore 报告 applied 且 activation/selection 构造完成后才替换 Manifest 与 Admission。rejected、malformed report、resource limit 或 owner 失败进入 typed apply failure并保持 fail-closed admission。Runtime Manifest、Agent Activation 与 Admission Authority 都不是第二份 durable truth。

每次 mutation 从 canonical desired 构建 immutable target并先完成 registry commit。`rename` 与 tool-only 等无 transport effect 的变更可以直接复用或重建当前 authority；loaded server 的启停/删除、启用未加载 server 或连接配置变化由 coordinator 自动进入 declarative apply。明确 commit failure 保持旧 desired/authority；saved recovery required 冻结后续 mutation；outcome unknown 不宣称 canonical desired/generation并安装 blocked authority。正式 apply 成功只影响后续新 Task；既有 Session 保持 AgentCore 已同步复制的 authority，不热替换或即时撤权。

启动按 `credential transaction recovery → oauth_operation recovery → schema migration/Workbench Desired preparation → canonical empty Agent Runtime ownership commit → zero-entry Runtime Manifest install → Workbench/coordinator install → initial configuration apply start → refresh timer arm → Bridge ingress` 线性化。遗留 `oauth_operation` 不重放，绑定 server 直接进入 `reauth_required`；schema 1 迁移统一 disabled + unapproved。启动 Preparation 的 credential staging 在进入 Workbench 前释放；initial apply 从 canonical Desired 重新 preparation，并沿与后续 mutation 相同的 coordinator 路径构造完整 replacement、调用 AgentCore apply、执行 activation，再原子安装 Manifest、Activation 与 Admission。Manifest candidate 的 `loaded` entry 只有在 opaque transport/input 被 Agent Runtime 完整接管后才能提交。Preparation 的预期 registry/approval/credential 故障形成 MCP unavailable/degraded；OOM 和内部不变量仍按对应调用边界 fail closed。AgentCore `runtimeCreate` 失败始终终止 Application 启动；empty Runtime 是唯一正式启动输入，不是对一次含 MCP Runtime 创建失败的猜测或重试。外部 MCP child、network、handshake 与 catalog discovery 只发生在 initial apply worker，失败不关闭普通 Task admission。

Admission Authority 是 `ready(optional opaque owned selection, catalog generation) | blocked(reason)`；`ready(null)` 表示已验证的空 authority，blocked reason 至少覆盖 pending restart、refreshing、activation unavailable、persistence outcome unknown 与 shutting down。初始 apply 期间 blocked authority 对 MCP fail closed，但 `selectionForNewTask` 向 canonical empty Runtime 提供 null selection，所以普通 Task 不等待 MCP；apply 完成前创建的 Session 保持空 authority，成功完成后只有新 Session 取得新 selection。新 Session 只能在 Workbench admission 边界同步借用 selection，AgentCore 在 create 调用内复制后不再引用 Workbench selection。MCP mutation、refresh、OAuth operation、运行时 reauthorization fact 和新 Task admission 使用 Workbench 同一短事务串行化边界；浏览器等待和网络请求不持锁，只携带 server-bound operation id。OAuth operation 若命中当前 authority，先预构建排除目标 server 的 selection，marker commit 后 no-fail 安装 reduced authority；因此其他 server 与普通 Task 不冻结，目标 server 在成功恢复 candidate 前不进入后续新 Task。运行时 challenge 也先按 consent epoch 与被拒绝的 token revision 校验：已轮换旧 token 的普通拒绝是 stale，新增 scope requirement 则并入当前 consent 的后续 authorization。Workbench 在 durable commit 前同时构造 owned pending-scope candidate 与 Admission candidate；`reauth_required` 明确保存后只做无失败安装，不再引用旧 Desired arena。每个成功 Desired install 都集中 reconcile pending state，删除已移除 server、已替换 consent epoch 或已把 scopes 固化到新 consent 的记录。内部 fact ownership/容量失败设置 process-lifetime Admission latch，后续 mutation 和 activation rebuild 都不能静默重开 authority；原失败请求不自动重放。活跃 operation 拒绝目标 server mutation，其他 server target 必须保留 marker；结果返回时以 operation id 和 server fingerprints 对当前 canonical registry 重新授权，并从当前 generation 提交，不要求起始 global generation 未变化。Cancel 在外部请求前可清除 ephemeral state；请求可能已发送后必须把目标 server 提交为 `reauth_required` 并保持 reduced authority。首版全局最多一个 OAuth operation。`recovery_required` 或 `outcome_unknown` 保留唯一 journal/marker 并冻结后续 mutation。关闭先停止 Bridge ingress、OAuth timer/callback、management、refresh 与 Task admission，释放 Admission Authority 和 Activation，再收口 callback，最后由 owner 逆序释放 MCP transport 与 Runtime。

refresh timer 是 Workbench 注入的独立单次 monotonic capability。Activation 提交时，Workbench 只把其中最早的可安全调度 catalog TTL 转换一次为绝对 monotonic deadline并留出提前量；configuration apply、OAuth operation 与显式 refresh 可以取消当前 timer effect，但不得用原始相对 TTL 重新计时。timer、显式命令与新建/恢复 Session 的 typed freshness failure 都先递增内存 request generation并记录 pending，再尝试把唯一 refresh job 入 Workbench 有界 executor；refresh、apply 或 OAuth 已占用边界时只延后执行，完成后消费 pending，不能丢弃触发。成功 apply 已包含 official activation，因此同时满足 apply 期间积累的 refresh 请求；普通 refresh 只有 request generation 仍为当前值时才能原子安装新 Activation/Admission。三十秒及以下 TTL 不进入后台主动刷新，避免形成高频全量刷新循环。

若 AgentCore 在新建或恢复 Session 的 admission 线性化点返回 typed `mcp_not_refreshed`，Agent 必须保留为 `McpNotRefreshed`，Workbench 立即封锁旧 Admission 并异步刷新；新建 Task 向本次请求返回 catalog loading，恢复 Task 保留可重试失败事实，二者都不得折叠成连接失败或自动重放原 mutation。

Workbench preparation 按 transport、auth mode、approval/consent epoch 校验 credential locators 与每服务 aggregate runtime secret limit；Application 是 transport auth snapshot 限制的真源并负责注入。Connection approval 前，Application 不得启动 child、解析 credential 或发网络请求；OAuth discovery 只能在 approval 后以无凭据有界请求运行。DCR、authorization-code exchange 与 refresh 都先 durable commit 同一 `oauth_operation` marker，外部请求后只允许提交 issued client identity/fresh locators；明确且未创建 client 的 DCR rejection 回到 `client_registration_required`，`invalid_grant`、response/persistence outcome unknown 与遗留 marker 进入 `reauth_required`。同 consent epoch 的 token revision 以 CAS 替换 ref-counted HTTP auth snapshot，旧 token 在最后一个 in-flight lease 释放后清零；新 consent epoch、connection 或 static secret 变化不得热替换 Runtime descriptor。Application HTTP capability 只处理 OAuth/auth、connection 与原始字节泵；Content-Type 分类、MCP session/status/header 规则和 SSE framing 归 Agent HTTP backend。STDIO 的 child/pipe/stderr/timeout effect 同样留在 Application，newline framing 与消息 bound 归 Agent。JSON-RPC identity 和消息语义仍完全归 AgentCore。

Static credential locator 归接收它的目标，而不是孤立的 environment/header name：STDIO 目标由 command、ordered argv 与 cwd 共同确定，environment slot name 精确匹配；HTTP 目标由 endpoint 确定，header field name 按 HTTP 大小写不敏感语义匹配。Replace mutation 只有在目标和 auth mode 未改变时才按同一 slot 沿用 locator；其余 locator 由全 registry 引用差分在同一 credential journal 事务退休。Renderer 以 Host 发布的完整非敏感 typed connection 预填编辑，并仍提交完整 replacement；它不读取或提交任何 secret value/locator。

Desired `enabled` 只表达用户意图，不重复承担 connection approval、auth readiness 或结构校验。已批准但缺 credential 的 enabled server 保持 desired intent，由 preparation 形成 missing-authentication absence proof 并排除出 Runtime/Admission；secure-capture capability 只决定 Host 能否执行采集，不删减 registry 可表达的 auth mode。

## 2. 领域状态与业务事务

### 2.1 Account 与 ExecutionConfig

Account 和 Workbench 是同级 owner，彼此不导入 runtime。Account Runtime 独占 OAuth token、PKCE、当前 `/me` 验证的 identity、Metask 完整 API Key、用户 Model Connection registry、平台凭据 locator、catalog attempt、mailbox/effect queue、当前默认选择和 credential generation；其内部状态、事务、catalog slot、提交与恢复只由 [Account 内部架构](account-architecture.md)定义。Workbench 独占已安装的默认 runtime ExecutionConfig、live Session/Run/job/worker 所需的 owned config、Task admission、Workspace/Task/Run history与 replacement gate。ExecutionConfig 的运行时数据流是 Account resolve → Application coordinator controlled transfer → Workbench execution-scoped ownership → Agent Session consumption；Agent 不查询 Account 当前状态。Bridge 只提交无 secret 的 catalog/connection selection identifier、严格解码后的 expected catalog/execution generation 或 typed `ModelConnectionCommand`；Renderer 不能把 provider、base URL、完整 credential 或未被 Host 验证的执行配置直接注入 AgentCore。

`src/product/account.zig` 与 `src/product/account/` 共同构成 Account Product owner；源码迁移不改变 `metawork_account` / `metawork_account_contract` 模块 identity，也不创建统一 Product facade。Account 通过自身 `ports.zig` 只声明并消费 refresh-token credential、preference persistence、authorization URL、timer 与 Model Connection credential vault；Application 在 `account_platform_binding.zig` 中绑定 Native SDK、主线程和有界文件 I/O，并在 Account shutdown 清空 port 引用后释放 binding。Preference codec、commit/recovery transaction、Model Connection registry、FileStore、原子提交与 persistence health 仍归 Account；Application 不因执行系统 effect 而取得这些产品 policy。

`src/product/task.zig` 与 `src/product/task/` 是同一 Product owner 持有的 live Task aggregate 边界。聚合入口只发布 Runtime、组合层所需的 typed operation/port/fact 以及 history/checkpoint store 叶面；state、policy、view、attachment、Session、execution、deletion 与 recovery kernel 不构成组合层可拼装的生产 API，仅在 `builtin.is_test` 下提供 fixture seam。`agent_session.zig` 是 Task 对 Agent Session 的唯一 capability gateway：线性 `Binding` 保存 Runtime slot 归还责任与 route identity，线性 `Access` 以 Agent `active_refs` 覆盖一次同步调用或 worker 内实际 Session 操作区间；wrapper 本身不分配，但底层 Agent API 保留各自 allocation/ownership 合同。`state.zig` 拥有 Task aggregate、Run/Compact record、Agent event 的产品状态转换、终态可见性与 final event-drain gate；`policy.zig` 无外部 effect 地处理 Agent Run/Compact/begin/checkpoint terminal 分类、interruption/cause 映射、Task lifecycle/active-operation/continuation/recovery query 与 Session disposition transition；`persistence.zig` 拥有 Task history capability/health、逐字段 Task/Run/Tool/Compact/UI/checkpoint wire projection、恢复重建、enum 与跨记录校验；`view.zig` 无状态地派生并编码 Renderer Bridge revision 1 snapshot 的 Task/Run/Compact/pending-UI/UI-history 子树；其余子模块拥有 checkpoint record/store、owned execution binding、runtime attachment、deletion policy、recovery policy 与 recovery job。canonical history 的 Workspace frame 仍由组合层提供，Task persistence 不接管 Workspace aggregate。它们可以消费 Account contract、Product Skill catalog 与 Agent 公共类型，但不得依赖 Application、Bridge、Native SDK、AgentCore 或产品组合实现。Workbench 仍独占 executor 本体、Agent event pump、跨 owner authority/admission、durable commit 实现、revision 与完整 snapshot 根编排；Runtime 通过 callback-scoped ports 请求 enqueue、commit、projection、notification 与 authority，不转移 allocator、credential、Session 或组合对象所有权。

`product/task/runtime.zig` 是 live Task aggregate 的唯一存储与行为入口，持有有界 Task collection、identity/recent order、failure ledger、attachment/operation、late-terminal、recovery 与 Agent shutdown facts，并闭合 Task create、Run/Compact start/cancel、UI response、model selection、detach、recovery、event application、Task 子树派生与 shutdown transition。原 per-Task `attached | detached | closing` resource union 归 `attachment.zig`；Workbench 只持一个 Runtime，不再平行持有散字段或直接调用内部 kernel。共享 Workspace+Task history health 与唯一 commit effect 仍归组合层；Runtime 只观察 `committed | failed | outcome_unknown` typed 结果，definite failure 回滚 Runtime 已准备的候选，unknown 则永久冻结后续 Task mutation。restore candidate 完成时必须一次校验 attempt、Task/binding、Workspace id/epoch/root、execution generation/model/provider、Skill revision、MCP generation、checkpoint、attachment、shutdown 与 projection budget；任一 token stale 都只丢弃 candidate，不自动重试。

Run 与 Compact 的产品记录只保存稳定状态、终态发布与取消 identity，不保存指回组合对象的 `Workbench`、`TaskView` 或 Agent `Session` 指针。executor 为每次入队持有独立且短寿命的 Run/Compact job context，其中持有 exactly-once Task `Access` 与执行所需的 Task/组合 capability；queued cancel 以产品记录地址匹配 identity，并同步调用 context 的取消回调，worker 执行或 queued cancel 负责精确一次释放 Access 并销毁 context。checkpoint postprocess 可以继续延长 Task worker reference，但不延长 job context：worker 完成后，主线程只凭当前 Task 遍历及记录内的 checkpoint 状态结算该引用。

OAuth loopback 采用同一切割纪律：Account `loopback.zig` 定义 endpoint/sink，并拥有 callback path、state、code/error、issuer、无效请求预算与 response policy；Application `oauth_loopback_transport.zig` 拥有 listener、connection、accept/receive deadline、跨线程 cancellation 与 HTTP byte pump。Account LoginAttempt worker 只借稳定 endpoint capability，MCP OAuth 在 Application 内直接复用 concrete transport；两条路径都不转移 socket、reader 或 request handle，sink 只在 callback 期间借用 request metadata。

公开 `AccountView` 只包含四态 `checking | signed_out | authorizing | authenticated` 和独立目录状态 `unavailable | loading | choosing | ready | failed`。`canCancel` 与 `canCreateTask` 是 Host 判定的能力事实，不再由 Renderer 从 operation/readiness 推导。saved account、reauth required、account mismatch、primary action 和公开 execution state 均不存在；登录无效直接变为 `signed_out`，统一通过 `beginLogin` 建立新 identity。

Model Connection projection 不扩展 Metask OAuth 状态机：每条连接发布稳定的非 secret `connection_id`、display name、provider、脱敏 normalized endpoint、credential status、bounded model metadata、generation readiness、latest test status 和 connection generation。Connection registry metadata 使用独立原子 store；API credential 只存在系统安全存储和当前运行时的 bounded owned copy。新增连接在 Account 内先 durable 提交 credential cleanup tombstone，再写系统 credential，最后原子地用完整连接替换 tombstone；Application 的 trusted capture continuation 只能同步借用 secret 并接收最终 typed result，Bridge 永远看不到中间 slot 或 secret。连接测试通过 AgentCore 的一次性流式 Completion 完成；该短寿命 owner 独立于 Runtime、Session 和 AgentLoop，测试 candidate 不进入 Workbench Task、Run history、Conversation 或 durable attachment。

`execution replacement gate` 区分两类操作：

- 默认 API、provider 或 credential 变化可以安装新 generation，既有 Task 继续引用旧 generation；同一已提交 API 下的默认模型变化只持久化 Account preference，不改变 credential generation、不安装 Workbench execution。两类操作都只暂停相关的新 Task admission，不冻结既有 Task、导航或历史；
- Model Connection 的新增、编辑、验证、启用、禁用和删除使用独立的 connection transaction；它可以在 Metask `signed_out` 时继续管理，但安装为默认执行配置前必须通过同一 generation/replacement gate。endpoint、provider 或 credential 替换生成新的 connection generation，不能原地改变 live Session；
- 账号 identity 切换、退出登录和设备 credential 清理只替换 Account 当前身份与 Metask-owned 默认执行配置，不等待、终止或改写既有 Task、Session、Run、job 与 worker reference。Workbench identity gate 只串行化这次 Account replacement；live Task/Session 已经取得的 owned ExecutionConfig 按原生命周期收口，退出登录不宣称对其热撤权。durable Task 和历史记录不持有 credential，也不参与 gate。

冷启动恢复不是运行中的 identity 切换：新进程先从独立 registry/credential store 恢复 durable Model Connection default，再并行恢复 Metask identity/catalog；Metask execution completion 只更新其自身状态，不能覆盖已恢复的 custom default。没有 custom default 时，Metask execution 才通过 default-execution transaction 安装。运行中的显式重新登录或 logout 必须经过 identity gate；该 gate 只清理 Metask-owned credential/default，不撤销独立的 custom default。显式切回 Metask 先重建当前 Metask execution，成功后原子清除 durable custom default并安装 Metask execution；任一步失败都继续保留 custom default。live Task/Run 已拥有的 ExecutionConfig 按原生命周期收口。

唯一 committed-state 写路径为：

```text
Account Runtime.prepare(command | completion)
→ Account effect admission
→ Workbench.commitAccountFactNoFail(...)
→ Workbench.installDefaultExecutionNoFail(...)  [可选]
→ Account Runtime.commit(prepared)
→ dispatch committed Account effect
```

前五步由 Application coordinator 在主线程同一 turn 内完成，effect 只有在 committed swap 后才能启动；worker completion 再经主循环进入同一条链。任何校验或内部不变量失败都保留旧 committed state，并清零 staged secret；Bridge 不参与 prepare/commit，也不接触 credential。C1 登录只依赖锁定的 OAuth client/scope/loopback、token rotation 和严格 `/me` identity，不等待 API Key 或模型目录。授权码交换产生新 token 后先提交 refresh token，再以已提交 generation 读取 `/me`；两步不得合成一个可回退结果。

Renderer catalog selection 的同步拒绝顺序固定为：Bridge authority/wire validation，Account Runtime generation 与 published membership validation，Account prepare，Workbench default replacement gate，最后进入上述 commit 链。Account 独占 identity、selection、catalog 与 attempt 合法性；Workbench 独占 replacement gate；Application coordinator 只安排顺序。`prepare` 成功但 gate 拒绝时必须销毁 prepared transition，不能提交 Account fact 或启动 effect。初始 effect admission 失败直接回滚并关闭新开的 gate；异步 continuation 的 effect admission 失败必须先提交已经观察到的前一步外部结果，再从该 committed phase 生成 terminal failure，确保 token 已提交后的失败不会错误恢复旧 identity/default，并在所有路径释放对应 gate。

verified identity commit 是 C1 完成边界，不是 Workbench 可见性门槛，也不要求用户手动启动 C2。C1 完成后 Account Runtime 直接产生 catalog command；catalog 失败保持 `authenticated + failed`，不回滚登录。历史选择仍存在且匹配当前 account/catalog 时优先恢复，单一候选自动采用，只有真实歧义才进入 `choosing`。Renderer 不观察状态后发送隐藏命令。

每个 Account attempt 都有 Host-owned deadline、attempt identity 和唯一 terminal completion。浏览器未回调、网络悬挂、effect 启动失败和取消都必须收口到可恢复 committed state。幂等 catalog read 可以有限重试；OAuth code exchange、凭据持久化和结果不确定 mutation 不得自动重放。进入 credential persistence 前允许取消；持久化 effect 开始后撤销 cancel admission，直到 main thread 原子消费 completion，避免磁盘已提交而内存被取消回滚。Renderer command timeout 只释放本地交互并触发 snapshot resync，不能代表 Host mutation 失败。

Metask managed 网络接入受 [Metask Account API 合同](metask-account-contract.md)约束。C1 OAuth/login 先独立提交 token rotation，再严格提交 `/me` identity；C2 使用无 Profile header 的 OAuth API Key catalog 与直接 API Key model catalog，从精确 `group.platform` 生成固定 Metask AgentCore target。用户 Model Connection 使用独立的 typed endpoint/credential/model 合同，只允许 Anthropic Messages、OpenAI Chat Completions 和 Gemini Native；不在本地实现 provider transport 或支持未登记协议。持久化只允许 secure store 中的 refresh token 和 Model Connection API credential，以及原子、无 secret 的 Metask selection/connection metadata；其中 generation 是没有顺序语义的随机不透明 binding nonce。access token、Provider API Key、custom credential、saved identity 和完整 execution config 不跨进程。冷启动先刷新 OAuth、提交 rotation，再以当前 token `/me` 结果建立 identity，最后决定是否复用 Metask preference 和可用 Model Connection。

进入 Workbench 后的 API、默认模型或连接切换仍由 Account owner 执行，不是 Renderer preference。Metask API/provider/credential 变化用当前 OAuth 重新加载 authenticated API catalog，不能复用已 secure-zero 的旧 private catalog；成功后才原子安装新 generation 并提升 candidate，其他 terminal outcome 丢弃 candidate 并回到旧默认配置。同一已提交 API 下的默认模型变化只以 committed catalog 校验并持久化 preference，generation 和 Workbench credential execution 保持不变。Model Connection mutation使用独立的 private/committed registry candidate。Account projection 发布候选目录或连接的脱敏 identity，Renderer 只能从 Host-owned projection 选择模型/连接。两类默认变化都只影响之后创建的 Task，既有 Task 继续使用自身 binding epoch。

durable Task/Run 只保存 Workspace binding、Provider、model 和 opaque execution generation 等历史事实；不得保存 account identity、Model Connection identity、API Key metadata、custom credential、credential locator 或可重建 secret 的信息。跨 Host 重启的 Task 先恢复成只读 projection，不创建 Session 或 Conversation。Schedule 在触发时如果保存的 execution generation 与当前默认配置不一致，进入 `needs_attention`；它不能阻止登录、替换 identity 或清除 credential。

因此 identity replacement、default execution replacement 与 durable history 是三个边界：前两者只处理真实运行时资源，后者只负责解释历史，不能反向成为 Account gate。

### 2.2 Workspace 与 Task admission

Workspace 是 Workbench-owned 产品对象，而不是 Renderer 从 Task 路径派生的 convenience view。Workspace record 具有 immutable `kind = manual | automatic`：Manual Workspace 由用户选择或重新授权，一个 record 可承载零到多个共享文件上下文的 Task；Automatic Workspace 由 Workbench 分配，一个 record 精确归属一个 Task。两者共用同一个 registry、Task 引用和 AgentCore Session admission；`kind` 只表达目录取得方式，不替代 authorization、Task ownership 或生命周期事实。Product 的 canonical projection 发布 stable identity、kind、optimistic epoch、canonical root、display label、authorization/removal outcome 与聚合 Task signals；每个 Task 引用的 Automatic Workspace 必须在同一 projection 中存在。一次性用户目录能力由 Bridge/Native capability 生成并在同一 `workspaces.choose` Host 命令内消费，Renderer 只得到 Workspace identity；automatic root/path/key 永不进入 Renderer 请求。Task 创建绑定 expected execution generation，后续 Run 绑定 expected binding epoch，Workspace mutation 绑定 expected Workspace epoch；Host 对 window、ownership、catalog membership 与 admission 重新校验。预期业务拒绝编码为 typed result，非法 payload 与 authority failure 仍由 Bridge fail closed；精确 wire 语义见 [Renderer Bridge 合同](renderer-bridge-contract.md)。

Application 使用现有 `app_dirs.resolveOne(..., .data)` 结果派生 `workspaces` 保留根，并在启动时尝试创建、canonicalize 和打开该目录。失败只投影 `automaticWorkspaces = false`，不得阻止 Account、Manual Workspace 或普通 Workbench 启动。成功后 Workbench-owned `AutomaticWorkspaceAllocator` 只通过已打开的 root handle 相对创建随机 `u64` 的 16 位小写 hex 子目录，exclusive create 最多尝试 8 次，并验证结果严格位于 canonical automatic root。automatic root 及其子目录不得注册为 Manual Workspace；分配失败不得回退到 cwd、home 或共享目录。

Workbench 的 Task workspace request 直接使用 `manual(workspace_id, expected_epoch) | automatic`；Renderer/Bridge 提交相同语义，不保留 `existing/managed` 内部别名，交互式 New task 与 Scheduled Task 也不建立第二条 Task 创建路径。Manual intent 在 Task 创建事务内重新校验 identity、epoch 与 authorization，并原子更新 recent order；Renderer 对工作目录控件的切换只更新 New task draft，不发送独立 Host selection mutation。Automatic admission 先证明 execution、Task slot、Automatic Workspace slot、Session 与 shutdown capacity，再创建目录、注册 `kind=automatic` temporary Workspace、创建 Session 并发布 Task；发布前任何失败用局部 rollback/`errdefer` 释放 Session/record 并删除本次创建且仍为空的目录，发布后的 Run 失败不回滚 Task 或目录。Manual Workspace record capacity 与 `max_tasks` 约束的 Automatic record capacity 分槽，后台创建不修改 Manual recent order 或 Renderer draft scope。owning Task 物理删除且 Run event、worker、Session 与 catalog 全部 quiescent 后释放 Automatic record，但不删除真实目录；shutdown 与重启也只释放进程内 record，不扫描、接管或删除旧目录。目录持久存在不是 Task 恢复协议。

Application 在 composition 时只解析一次 existing canonical user home，并以 immutable capability 注入 Workbench；Renderer、Bridge payload 和 Workspace selection 都不能覆盖。Product Skill Runtime 经窄 ports 把 AgentCore catalog discovery 提交到现有 bounded Executor：worker 只产生 Agent-owned acquisition，Runtime 按 Workspace id、epoch 和 request generation 提交或丢弃；Workbench 不持有 catalog job。Manual Workspace current Skill authority 是 tagged slot：`committed` 分支不可分地持有唯一 opaque lease 与已按产品 policy 编译的 immutable bounded snapshot，`uninitialized | unavailable` 分支不携带可执行 authority；catalog job 独立表达进行中的 refresh。refresh 期间继续服务 last-good committed authority，incomplete、编译失败或查询失败不能用空 catalog 或半状态替换 current；当前不保留或投影最近一次 refresh 失败事实，该可观测性作为后续独立产品议题。只有首次没有 committed authority 时 Skill unavailable，Text 路径仍可用。Task 创建在 Agent Session 前完成容量证明并复制独立 pinned projection，同步借用 current lease 绑定 Session。首期 Automatic Workspace 只接纳 Text Task，不启动 Workspace catalog job、不发布 refresh 动作，并以 null catalog lease 创建 Session；Skill automatic admission fail closed，直到 root-specific acquisition、identity、容量和 shutdown 通过独立验收。Task refresh 只从已经提交的 Manual Workspace authority 进行、只允许 idle Session，并在 Agent refresh 成功后替换 pinned projection。shutdown 先令 Product Skill Runtime 停止接纳并取消 queued catalog job，再停止/join shared Executor；Runtime 随后收口 completion 并释放全部 Workspace lease，最后才允许 Agent Runtime destroy；不建立第二 scheduler、隐式文件监听或 Renderer Skill loader。

Task 标题仍由 Workbench 独占。首个 Run admission 在标题为空时立即用既有首个 Text 安全行或 Skill display name 规则提交临时标题，同时冻结一份同一 Task ExecutionConfig；Run terminal 发布后，同一 executor worker 使用 Agent 公共表面的独立流式 Completion 生成有界标题候选，不创建新的 Session、Run、Conversation 或历史记录，也不改变 terminal fact。主线程只在该值仍由自动标题流程拥有且候选仍属于 generation 1 时替换；用户 rename、预置标题或后续结果都优先并使候选失效。Completion 失败、超时、非 `end_turn`、非法或多行输出和 shutdown abort 均保留临时标题；标题提交继续执行 credential redaction 和 Task persistence，短寿命 ExecutionConfig 在 Stream → Completion quiescent 后 secure-zero。

### 2.3 Scheduled Task

Scheduled Task 是 Workbench 内新的可测试不变量，不是第六个 product module。`workbench/scheduled_tasks.zig` 拥有结构化 recurrence、bounded definition/occurrence storage、跨恢复稳定的 `(scheduledTaskId, plannedAt)` identity 与纯状态转换；独立的 `workbench/scheduled_task_persistence.zig` 拥有无 secret codec、原子 candidate commit、恢复校验和 schema revision。定义只保存名称、Text instruction、recurrence 与无 secret execution facts，不保存 Workspace target、Skill identity、catalog revision 或 Skill 参数；需要 Skill 的意图仍属于 instruction，occurrence 只生成普通 Text Run。`projection.zig` 在每个 occurrence 中固定请求新的 Automatic Workspace，再进入真实 Task admission。当前仍处于 pre-release 开发期，Scheduled Task persistence schema 固定为 `1` 并对定义结构原地 hard cut：只接受当前 shape，不保留旧字段的解析、双写或迁移；旧开发数据按现有损坏恢复路径处理。

Application 只注入平台 capability：产品数据目录中的原子读写、wall clock、单一 Native timer、notification，以及 tray/hidden-window 生命周期。主窗口 `close_policy = hide` 后 Application、Workbench、Executor 与 timer 都保持存活；tray 是重新打开窗口和显式退出的唯一入口。后台不是 Renderer timer，也不是 Agent Runtime capability。Application 重启时必须先恢复并校验 canonical Schedule store，再 arm 最早 due time；若最近计划时间已经过去，只对每条定义协调一个最新 occurrence，不遍历补跑全部历史。store 损坏或提交结果不确定时 fail closed，保留可诊断 persistence health，不能假装成空列表。

到期回调在主线程要求 Workbench 最多提交一个 occurrence，再为下一次 due time 重新 arm。成功 occurrence 调用既有 Task 创建、命名与 `runTaskAtBinding`，因此复用同一 Session、Run record、Executor、event pump、permission 和 snapshot 路径；不能新增绕开 admission 的 schedule queue、schedule worker 或直接 AgentCore call。系统通知只消费已经提交的 Workbench occurrence/Task fact，通知失败不得伪造 Run cause或回滚 terminal fact。

### 2.4 Skill catalog 与本地资产管理

Workbench `TaskRunInput` 只有 Text/Skill 两个分支。Skill admission 在建立 Run record 前校验 Workspace/Task epoch、pinned revision、稳定 `skill_id`、参数数量、UTF-8 与产品容量；Run history 保存 admission 时的 invocation/display/arguments，不随后续 catalog 改写。AgentCore 仍负责最终参数、资源和 policy 校验；`stale_catalog`、`skill_not_found`、`invalid_skill_arguments`、`skill_policy_violation` 与 `skill_unavailable` 形成独立产品 cause，保持 Session 可复用且不自动刷新或重放。

Skill 中心在 revision 9 typed catalog 之外增加 Product Skill-owned 本地资产管理层，但不形成新的产品 owner、AgentCore loader 或 Session execution binding。`product/skill/package.zig` 独占本地 Skill 目录与 canonical `.skill` ZIP 的路径/资源上限预检、regular-bytes-only staging、内容摘要和导入导出，不执行包内容或访问网络；`product/skill/management.zig` 拥有 personal/project inventory 与 transaction 实现、安装 provenance、独立 `install_id`、canonical-root 原子 publish/rollback、recovery 和持久 store，并消费同一 Product Skill package kernel；`product/skill/state.zig` 持有 live inventory/transaction、management/enablement health、staging root 与 reconciliation latch。Application 直接创建并持有 management `FileStore`，同时只注入 canonical user home、产品数据目录与 Native file/folder picker；Bridge 直接消费 management 的 data-only identity/scope 类型，Renderer 不持有物理路径。`agent/catalog.zig` 继续独占 AgentCore query/lease 与运行时 projection；catalog member/run identity 使用 concrete `skill_id`，跨 catalog 内容 revision 的启用策略身份使用 AgentCore `skill_policy_key`，两者都不得被 `install_id`、目录名或 Renderer 推导的 invocation 取代。管理 inventory 可以在已经授权的 canonical `<home>/.agents/skills` 和 `<workspace>/.agents/skills` 内枚举直接 Skill entry、读取受限 package 内容并建立 provenance，但不得自行决定 runtime winner、conflict、health 或 catalog revision；这些结果只来自 Product Skill Runtime 经窄 Agent catalog port 发起、并由内部 management runtime 完成 reconciliation 的正式路径。

`product/skill/enablement.zig` 独占用户默认 + Manual Workspace 覆盖 policy 与 `skill-enablement.json` schema 1 store。快速开发阶段直接原地 hard cut schema 1 内容，不解析或迁移旧 shape，也不提升 schema version。store 以全局 `last_revision` 分配 mutation revision；user record 保存 disabled `skill_policy_key`，Workspace record 保存 `workspace_id + workspace_epoch`、effective `policy_revision` 和互斥的 enabled/disabled policy-key overrides，缺少 override 表示 inherit。用户 mutation 给 user 与所有现存 Workspace record 盖同一个新 revision；项目 mutation 只推进目标 Workspace；no-op 不推进。`product/skill/policy.zig` 负责 persistence failure 到 health/authority invalidation 的纯决策、scope invocation 查询，以及按 `Workspace override > user default > enabled` 计算 selection revision 与 disabled policy keys；它调用 `catalog.zig` 一次编译/重编译 immutable authority，但不执行 persistence、catalog acquisition 或 publication。`product/skill/runtime.zig` 持有 `state.State`、Personal/Workspace current authority、request generation、catalog job 与 Workspace binding；committed authority 同时拥有 opaque lease 与 immutable snapshot，lease 释放只经窄 catalog port 回到 Agent。`product/skill/view.zig` 读取这些 state/policy/catalog/management facts，派生 revision 1 Skill catalog 与 management snapshot 子树；敏感文本写出和 Workspace scoped catalog 迭代只以 callback-scoped capability 借入，不保留 Workspace、secret、buffer 或 effect。Product Skill Runtime 拥有 catalog acquisition job 及其 refresh/reschedule/stale/shutdown 生命周期，也拥有 enablement CAS、candidate compile、persistence commit、authority swap 与 failure invalidation；它只借用 shared Executor 与 Agent catalog ports。Workspace/Task 生命周期、authority 校验、Executor 本体和线程仍不归 Product Skill。Workbench 再从 snapshot 中 enabled winners 生成 AgentCore `SkillPolicyV1.granted_skill_ids`，禁用 winner 不回退到被遮蔽候选。mutation 必须以对应 catalog、selection 和 Workspace epoch（若有）做 CAS。mutation 先 clone policy store，并为 Personal 以及所有具有 committed authority 的受影响 Workspace 预编译完整 candidate；任一 candidate 失败则不写 store，持久化明确成功后才无失败替换 store 与 authorities。没有 committed authority 的 Workspace 不进入 candidate 集合、不会锁死 user mutation，并在以后 catalog 成功时按最新 policy revision 编译。已经创建的 Task/Session 不随 toggle 自动重绑。read/corrupt/write/outcome-unknown 都 fail closed，不能降级为全启用；明确 write failure 保持旧 committed state，outcome unknown 冻结新的 Skill authority 与 admission，Text 路径保持可用。启动恢复在 Workbench ready 前清理不存在或 epoch 已变化的 Workspace record；Workspace 删除/重新授权事务提交后再次 reconciliation。Application 只直接打开并持有 Product Skill `FileStore` capability，再经 composition 注入 Product Skill Runtime；Workbench 不取得 concrete store 类型，也不执行 enablement encode/commit。Workbench 仍拥有完整 snapshot 根编排、容量 buffer、revision 与交付。

package、policy、state、view 与 management runtime 都是 Product Skill Runtime 的内部实现，不从 `product/skill.zig` 暴露；Workbench 只能通过 Runtime 的 typed operation、query 与 view API 使用这些事实，不得直接 import kernel 或读取 `.skill.state`。Runtime 不发布 `CatalogSlot`/`CatalogControl` 或其可变指针；跨 owner admission、Task refresh 与 recovery 只借用 immutable snapshot + Agent lease authority，所有 catalog redaction、invalidation、generation 与 reschedule 仍在 Runtime 内完成。enablement 与 management 仍作为 Application FileStore 和 Bridge data-only DTO 的窄叶面直接发布，不因此形成第二个 live aggregate。

当前本地来源只有 `local_package`、`local_directory` 与 `external`。普通 Task 写出的 Skill 没有可靠发布事件，因此不得虚构 `created` 来源：写入项目 Skill root 后表现为 external project asset，打包后再导入则按真实本地来源记录。公司市场未来只能作为新的 package acquisition adapter 接入同一 staged transaction；服务上线前不注册 wire tag、UI 占位、搜索、排名、在线更新或 GitHub/skills.sh 依赖。MetaWork 不建立中央 Skill repository、symlink/copy fanout、Agent adapter、Preset 或第二份 catalog。

`.skill` 是 MetaWork 的可交换 ZIP envelope；规范导出在 archive root 直接包含精确大小写的 `SKILL.md` 和同一 Skill 的相对资源。导入普通 `.zip` 时只允许 archive root 本身或唯一 wrapper directory 成为候选 Skill root；多个 `SKILL.md`、多个候选根或 root 缺失均失败。归档和目录 import 都必须在目标 root 之外 materialize 为 staged tree，并拒绝 absolute、drive/UNC、空、`.`、`..`、NUL、非 UTF-8、重复归一化、Windows 保留名/尾随点空格路径，拒绝 symlink、hardlink、device、socket、FIFO 与其他特殊 entry；当前合同上限为 512 个 regular files、64 MiB 解压总量、16 MiB 单文件、512 UTF-8 bytes 相对路径和 128 UTF-8 bytes 单 path component。`.skill` 压缩输入上限为 32 MiB。Importer 只读取/复制 regular bytes，不执行脚本、解析远程链接或发起网络请求；export 服从同一边界并使用稳定相对路径排序，不包含绝对路径、provenance store、credential、`.git` 或平台 metadata。

Import preview 使用一次性、window/source-bound opaque staged capability，并在 preview identity 中绑定 content hash、候选名、source kind、容量结果和 expiry；Renderer 提交的 commit 只能包含该 preview identity、显式 target `personal | project(workspace_id, expected_epoch)` 与冲突确认 generation。目标 entry 由 Host 从受限候选名生成且必须保持在 canonical Skill root 直接子级；Renderer 不能提交目录名或路径。Publish 在同一 filesystem 上用 sibling candidate 与 backup 进行 rename transaction：先重新验证 capability/hash/target/generation 和相关 active-operation gate，再把既有 target 移到唯一 backup、candidate 移入 target、执行 AgentCore catalog reconciliation，最后删除 backup。明确映射到候选 invocation/scope 的 definition/resource/conflict failure 会恢复 backup；catalog transport/runtime 暂不可验证时保留 target 与 backup transaction record，发布 `pending_verification`，只允许 Retry 或 Uninstall，不能声称 ready。恢复时 fail closed 地完成或回滚唯一 transaction；不扫描、接管或删除 root 外目录。

Personal mutation 在任一可能消费 personal catalog 的 Task 存在 active operation 时拒绝；project mutation 在目标 Workspace 的 Task 存在 active operation时拒绝。已经发布的 mutation 不热更新 Session：Workspace current 与顶层管理 catalog 通过显式 transaction 重查；Task pinned catalog、draft identity 和参数保持原值并进入 stale 提示，只有用户在 idle Task 上显式 refresh 并重新选择后才能提交新的 Skill Run。Uninstall 与 replacement 使用同一 gate/backup/reconciliation；external asset 只有在 inventory 能证明它是 canonical Skill root 的直接子级、没有 link/reparse escape 且持有对应 personal/workspace authority 时才开放导出或删除，否则只以 `externally_managed` 展示。

启用/禁用 mutation 只更新 Workspace current policy；已经创建的 Task 保留其 pinned catalog 与 pinned policy，运行 admission 同时校验两份 revision，disabled Skill 返回独立 `skill_unavailable`。idle Task 显式 refresh 通过 AgentCore `sessionBindSkillPolicy` 原子替换 catalog lease 与 typed policy。Host 重启恢复是 pinned 规则的显式例外：Task persistence 不新增 policy 字段，也不升级 history wire；恢复 job 查询 Workspace 当前 catalog、应用当前 committed policy，并将同一 policy 交给 Session restore 与新的 pinned projection，因此恢复后的 Run admission 使用这次重绑得到的 revision。

Skill management persistence 是 Product Skill-owned、无 secret、原子 candidate commit 的独立 schema 1 store。记录仅保存 `install_id`、source kind、目标 scope/workspace identity、Host-only target entry、content hash、安装/重新导入时间、management state 与未完成 transaction recovery facts；不保存 Skill body、raw path 到 Renderer、catalog handle、credential 或 Task binding。当前仍处于 pre-release，schema 原地 hard cut，不解析、双写或迁移被替代的开发 shape。对应 wire 与 transport 只由 [Renderer Bridge 合同](renderer-bridge-contract.md)定义。

Product Skill Runtime 同时拥有本地 package 与 management 用例。内部 `management_runtime.zig` 对任意选取路径执行有界目录/归档 preview，对 inventory 中已安装资产执行 definition 读取与 canonical `.skill` 导出，并闭合 install/reimport/uninstall/retry、staging、persistence failure、启动恢复和 catalog reconciliation。Runtime 根据已注册的 Personal/Workspace canonical binding 自行拼接、验证和打开 `.agents/skills`，不把 `CanonicalRoot` 或目录布局暴露给 Workbench。Workbench 只证明 scope 对应 Workspace authority 与相关 Task quiescence、提供当前时间事实并在成功后发布 revision；资产身份、健康门槛、canonical root、目标 entry、package 资源约束、文件事务与 reconciliation 决策都由 Product Skill 决定。平台 picker 仍只返回用户选择，不取得产品判断权。

### 2.5 Identity 与 credential redaction

Workbench 单独分配稳定的产品 Task identity，并在 Task owner 内保存 Agent Session route identity；AgentCore event 与 event-projection failure 都只按 route identity 回到 owner，Bridge snapshot 与 mutation 只使用产品 Task identity，二者不共享生成器也不依赖数值相等。durable Task binding descriptor 只包含 Workspace/binding epoch、Provider、model 与 opaque execution generation；account identity、Model Connection identity、API Key identity/metadata、connection credential locator 和完整 ExecutionConfig 只属于对应 owner 的当前进程运行时，不进入 Task store、Bridge 或 Renderer。
credential redaction 是 owner 释放协议的一部分，而不是 snapshot 时的偶然过滤。安装新 credential 前先永久清洗所有既有产品投影；替换或清空默认 execution、释放 quiescent Task-owned execution 前再次使用即将释放的 credential 清洗 Workspace、Task、Run、tool 与 UI history，然后才 secure-zero。序列化仍扫描所有 live credential，并在前缀重叠时采用最长匹配，作为释放前的第二道防线。credential 是 opaque bytes；若匹配发生在 UTF-8 codepoint 内部，所有 ingestion、流式跨 chunk 清洗与序列化路径都必须扩大到完整 codepoint，禁止为了替换 secret 产生非法 UTF-8 产品事实或 JSON。

## 3. 并发与生命周期

```text
SessionRuntime
├── AgentCore Session handle
├── Conversation 所在 AgentCore Session 生命周期
├── task binding epoch 对应的 owned ExecutionConfig generation
├── current_operation: none | RunJob | CompactJob
├── bounded input/event state
├── synchronous UI wait state
└── callback lifetime guard

RunJob
├── run_id
├── pending external interruption（Workbench admission/handoff 窗口）
├── executor slot
└── run-scoped Host scratch

CompactJob
├── monotonic operation_id
├── executor slot
├── advisory handoff / pending interruption
├── preallocated bounded terminal diagnostic storage
└── allocation-free write-once compact terminal publication
```

- 每个 Session 至多一个 in-flight operation；Run、manual compact、Session mutation 与 destroy 互斥；
- 每个 Session 在创建时绑定一个 immutable ExecutionConfig generation；默认 Account/Model Connection 配置变化不热替换 live Session，显式 Task rebind 也必须创建新 Session；
- Host 使用有上限的 Workbench executor；
- 空闲 Session 不占 worker；同步 Run、同步 UI wait 和 manual compact 占用 execution slot；
- Workbench 创建、排队、停止并销毁 bounded Executor；Agent Runtime 不接收 Scheduler capability，worker 从 Workbench queue 主动进入 Agent Run；
- Scheduled Task 的 recurrence、持久触发游标、wall clock 和 timer admission 由 Workbench 拥有；Application 只提供 store/timer/notification/tray capability。Workbench 只向同一 Task/Run Executor 提交真实产品工作，不把 scheduler capability 注入 Agent Runtime；
- Bridge/main thread 不执行长耗时 Run，也不等待 permission；
- 只有 `agent/` import `metask_agentcore`；Application 只组装 Agent，ABI discovery 由 Agent 内部完成，Workbench 通过 Agent 公共 validated types 消费，Bridge DTO 不暴露 SDK enum/owner/handle；
- `product/account/contract.zig` 不导入 Native SDK、Agent、Workbench、Bridge 或 AgentCore；Account Runtime 只消费 `product/account/ports.zig`，Application 的 `account_platform_binding.zig` 适配 Native SDK 与文件系统；Workbench/Bridge 只导入纯 contract，不导入 Account runtime；
- Account Runtime 的 committed shutdown effect 必须在 Native SDK runner 返回前取消 Account timer、join attempt worker 并清空 port 引用；Application 随后释放 platform binding，Account 的普通 `deinit` 只释放不依赖平台存活的内存；
- Agent 只通过有界 notifier 报告事件就绪，Application 负责把 wake 安全提交到平台主循环；精确状态、retry 与 deadline 见 [AgentCore 集成契约](agentcore-integration.md)；
- Renderer response、revision、snapshot 和 connection failure 作为 typed transport fact 进入 Workbench policy，默认只拒绝、重试或断开，不中止后台 Agent Run；
- MCP mutation、catalog refresh 与新 Task admission 共用 Workbench 的有界串行化边界；Task create 只在 authority 稳定时同步把当前 selection 交给 AgentCore 复制，持久化结果未确定、freshness-invalidating refresh pending、refresh in flight 或 shutdown 时不得取得旧 authority；仅由显式预刷新产生且尚未取得 Runtime 的 pending request 不提前撤销仍有效的 reduced authority；

AgentCore Session、callback、UI request、event pump、close race、错误映射与 Runtime 销毁顺序只由 [AgentCore 集成契约](agentcore-integration.md)定义。

## 4. 产品状态、持久化与恢复

当前同步 baseline 应形成以下可靠 Host 状态：

- 用户提交的消息；
- 已完成的 assistant 消息；
- 工具调用和结果；
- 同步审批决策；
- Run 的 running/waiting/stopped/completed/cancelled/failed/interrupted 状态；
- manual compact 的 queued/compacting/stopping 与 append-only terminal history；
- WebView reload 所需的当前 Host view snapshot。

`product/task/execution.zig` 独占 Run/Compact executor payload 与 execute/cancel callback。每个 job 只消费稳定 record、入队前取得的 scoped Session Access、notifier/completion/text-projection/checkpoint capability 与对应 worker-reference atomic，不保存 Workbench、Task aggregate 或 Task runtime 指针。自动标题 credential clone 归 Run job 线性所有，record 只保存状态/result facts；job destroy 在 queued cancel、执行完成和入队失败路径统一 secure-zero。

Workbench 在 admission 时为每个 Run 或 compact 建立稳定 record slot 和 bounded terminal diagnostic storage；Run 另有单调 generation，并拥有自己不可变的 `execution_model` 副本。checkpoint description 所需的 Task identity、binding epoch、model 与 last Run/compact identity 同时冻结进该 operation record，executor worker 在 terminal publication 后只消费这份不可变 context，不遍历 main-thread-owned durable arrays。executor worker 入队前直接取得 Task-owned stable record reference，并在 queued cancellation、执行失败或 terminal publication 收口后精确释放；需要生成 checkpoint 时，该引用延长到主线程提交 `CheckpointRecord` 或明确丢弃 candidate 后才释放。该真实引用非零时 Task record 不得物理释放。删除是 Workbench-owned、runtime-only 的独立用例，不进入 `RuntimeAttachment` 或 durable Task：`task_deletion` 只消费各 owner 的只读事实，并固定按 checkpoint → terminal event → Session release → worker reference → durable commit 的顺序选择唯一下一 effect；`projection` 在删除请求、checkpoint settle、Session close completion 与 lifecycle sync 后重复推进同一个用例。明确失败转为产品级 `failed` 并停止自动推进，只有用户显式重试才重新进入 `deleting`；Task store 提交失败必须恢复候选，命令受理只表示删除意图成立，不表示 durable record 已移除。Agent 对已开始的 operation 返回自包含、不可变的 terminal result；Workbench 将其 allocation-free、no-fail、write-once 地提交进预留 payload，`published` release-store 是唯一 terminal linearization point，完成前不得 notify、释放引用或调用外部 owner。queued-before-execute 由 Workbench 直接生成 pre-execution 产品结果。Session snapshot 只描述 live lifecycle，不再承载历史 terminal facts。

Compact 的 executor handoff 与 pending interruption 是 advisory control fact，不能覆盖 terminal payload。Workbench main thread 按 `terminal publication > pending interruption > worker handoff` 派生 `terminal / stopping / queued|compacting` 产品 phase；独立 cancellation atomic 即使在 terminal race 后被设置也必须被忽略。Compact 没有 Run event stream，因此不复制 Run 的 final event-drain product gate；snapshot acquire 到 published payload 后即可消费全部 terminal fields 和 diagnostic bytes。

Product Task 将 `DurableTaskRecord` 与 `RuntimeAttachment` 分开：前者拥有 Task 产品历史、归档标记和可选 `CheckpointRecord`，不保存 `closed` 产品终态；后者以 tagged union 独占 `agent_session.Binding`、ExecutionConfig/catalog lease，或明确表示 detached 且不持有这些资源。实际 Agent Session allocation/slot、AgentCore handle 与内部生命周期仍由 Agent Runtime 拥有，Task Binding 只拥有唯一使用与归还责任；普通 detach 必须先 `closeOutcome` 并 `releaseClosedSession`，不能丢弃 live Binding。进入 closing 时，Task 将 Binding 线性移入 close-worker 独占槽，同时在主线程侧保留不可变 route id，直到已入队 Agent event 与 terminal fact 全部 drain；close worker 不得原地改写主线程可路由或可借用的 Binding，主线程只有在 join 后才能提交 release、失败恢复或 shutdown relinquish。Run/Compact 内存 record 在 quiescent 前仍包含 terminal control 与临时 redaction secret；Task persistence codec 逐字段白名单编码无 secret 的 Workspace/Task/Run/tool/UI/compact 产品事实与 checkpoint record，pointer、path、opaque handle、raw description、atomic、control payload 和 credential 不进入 wire，Task execution 释放前同时清空 Run 与 Compact 的 secret 引用。Application 在 restore 前按固定顺序取得 `workbench-history.store` 与 checkpoint 目录的 OS exclusive writer lock；history 读取上限为 16 MiB，commit 使用同目录随机临时文件、file sync、原子 rename 和最终文件/目录 sync。checkpoint blob 位于 `<data dir>/workbench/checkpoints/<taskId>/<generation>-<digest>.ckpt`，采用有界流式写入和不可变命名。当前 store 不存在表示首次启动；旧 JSON envelope 不读取、不迁移、不双写；Task history restore 按 frame 独立扫描与校验，单个损坏 frame 被隔离并进入 `degraded` health，其他有效历史继续作为 canonical projection；只有 store 无法建立、definite write failure 与 outcome unknown 才关闭全局 Task mutation。Product Task persistence decoder 在组合层安装候选前校验正数 recent order、Run phase/outcome、Tool state/error、Compact→Run、Compact phase/cause、activity order 与 checkpoint record 等跨记录不变量，不能把 Renderer 必然拒绝的状态标为 ready。

Renderer reload 重建仍存活 Host 的视图；Host 重启从 Workbench store 重建产品历史与 detached attachment。没有 live owner 的 non-terminal Run/compact 保守收口为 interrupted，不重放输入、工具或 permission；任何恢复 Run 中未完成的 running Tool 都不进入 projection，已完成 Tool result 保留。完成态 Tool result 是 Run terminal 前的持久边界，text chunk 与 progress 只保留在 live projection。每个成功收口且 Session 仍可复用的 Run/compact 在 terminal product fact 发布后，由同一 executor job 同步流式 export；blob 必须先 durable commit，主线程随后才把 `CheckpointRecord` 提交进 Task history。新 record 明确失败时保留新 blob 为孤儿；提交结果不确定时保留 candidate、引用和全部 blob 并冻结 mutation，等待重启对账。可信启动先校验 record 对应 blob 的 size/hash，缺失或不匹配时先 durable 清除 record 并记录 typed health，再反向删除无 record 的 blob；Task history 为 `degraded` 时暂停 checkpoint 孤儿清理以保留未知 Task 的 blob；只有完整 store/read-write 状态恢复为可信且 checkpoint store 整体可用时才执行孤儿清理。

`CheckpointRecord` 嵌套三种不同来源的事实：`blob` 直接复用 checkpoint store 的 Task/generation/byte-size/SHA-256 identity；`session` 只保存 AgentCore `session_describe` 中有恢复消费者的 `logical_session_id`、`last_run_id`、`last_compact_id` 与 `model`；`anchor` 保存 Workbench 提交时的最新完整 Run/compact terminal 和 binding epoch。旧 `logical_id` 只是 digest hex，内存和 wire 均删除；`chunk_count` 只属于 export candidate metrics。持久 codec 原地 hard cut 为该嵌套 shape，不保留旧内部 layout、迁移或双读。checkpoint store 的 health 只描述目录打开与已完成的启动校验，不冒充一次 Agent restore 结果。

Conversation recovery 是 detached Task 的 attachment 重建事务，不是历史重放，也不新建 Product owner。Task 的 durable archive fact、`attached | detached` runtime attachment 与唯一 active operation 分离；continuation 可用性和 `continuationRecoveryAvailable` 完全从这三者、checkpoint health、Workspace authority、exact ExecutionConfig binding、Agent Runtime readiness 与当前 operation 派生，不保存第二套 recovery 状态。主线程 snapshot 只消费启动时已经形成的 checkpoint health，不执行最大 64 MiB 文件读取或 SHA-256；真正的 blob size/hash 再校验只在 recovery job 内完成。

用户显式发起 restore 后，Workbench 在主线程冻结 checkpoint identity、terminal/binding expectation、Workspace/Execution authority、Skill catalog revision 与 MCP selection，分配 attempt 和 stable worker reference，再提交同一 bounded Executor。job 不保留 Task/Workspace 指针：它独立取得 Skill catalog、按冻结 authority 构造 MCP selection、打开并验证同一个 checkpoint source，再调用 Agent restore。MCP selection stale、Skill catalog acquisition、checkpoint I/O、AgentCore restore、Runtime shutdown 与容量失败都作为 typed、可重试的 attempt 结果返回。restore 期间 Task 不能启动 Run、compact 或第二个 restore。

job 成功只产生含 `Binding`（内部封装 route id）与值类型 `CheckpointRestoreReport` 的 candidate，不暴露 `SessionRestoreRoute`，也不直接改变 Task。主线程 commit 再次精确校验 Task identity、attempt、binding epoch、checkpoint identity、Workspace/execution/catalog/MCP authority 和 durable terminal anchor；全部相等才以一次状态转换安装新的 attachment，否则先销毁 candidate 并保留 detached Task。成功 commit 后才发布 continuation available；失败保留历史和 checkpoint，并通过既有 continuation 原因发布可重试状态。恢复候选先使用 checkpoint 内的 logical Session identity 和历史 model 完成 AgentCore restore，再在 commit 前通过 scoped Access 切换到 Task 当前 model binding；Host 不向 AgentCore 提供逻辑 Session ID，也不能通过 restore 扩大 checkpoint 的历史 Workspace、Skill、MCP 或 permission authority。

关闭顺序固定为 Application 停止 ingress/协调器，再调用 `Workbench.shutdownExecutor()` 取消 queued/running restore 并等待 worker/Access quiescence，之后调用完整的 `Agent Runtime.shutdown()`。Agent Runtime 自己用 restore in-flight fence 保护 `session_restore`：锁内预留 Session slot 并计数，锁外执行流式 ABI 调用，返回后锁内对账；shutdown 必须等 restore、catalog、MCP、RunControl lease 与 Session `active_refs` 归零，再关闭 Sessions、检查 catalog leases 并销毁 Runtime。最终 event drain/lifecycle sync 后，Application 把 shutdown 成功事实交给 Product Task，使残留 Binding 单向进入 `relinquished`、清空 Runtime/Session identity 并永久拒绝 access/close/release；Application 不得拆开 Runtime 内部步骤。该能力只恢复正常 Application 重启后的 finalized Conversation boundary；独立 Worker crash、in-flight Run、async pending 与 suspend/resume 不在当前范围。

Account attempt 与 Renderer 生命周期解耦：Renderer reload、短暂断连或视图同步失败不能遗失 Host 中的 deadline、取消能力或 terminal result。Workbench Account projection 必须发布产品 readiness 和 Host 允许的用户动作；Renderer 不从内部 operation、error code 或候选数量自行发明 continuation。
