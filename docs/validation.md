# MetaWork 验证规范

> 状态：初始技术验证已经收口；本文维护当前验证状态、可复现命令、证据索引和覆盖缺口

本文是验证控制面，不是产品或技术设计文档。它只回答四个问题：验证什么、依据哪份规范、证据在哪里、还缺什么。产品行为以 [产品需求](requirements.md) 为准，系统决策以 [高层架构](architecture.md) 为准，AgentCore 生命周期和 ABI 分别以 [AgentCore 集成契约](agentcore-integration.md)与 [ABI v1 消费合同](agentcore-abi-v1.md)为准。

## 1. 状态含义

| 状态           | 含义                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| 已验证         | 在精确 commit、平台和 artifact 上有可定位执行证据；后续代码变化仍必须持续回归 |
| 自动化已覆盖   | 当前 test graph 有绑定到该不变量的确定性测试；不等同于真实平台或外部服务验收  |
| 人工验收待完成 | 实现和自动化可能存在，但真实窗口、平台、可访问性或产品判断尚无完整证据        |
| 尚未实现       | 只有需求或架构边界，不得从当前 baseline 推导为可用能力                        |

状态必须绑定证据，不能仅凭代码存在、关键词扫描或历史聊天记录升级。

普通自动化结果可由当前 test graph 重现，不进入长期证据账本，也不冠以会在下一次代码提交后立即失真的“当前回归”状态。提交是否通过由对应 commit 的真实执行结果负责；只有稳定发布、artifact migration 或无法由普通自动化重现的平台/外部服务事实保留在上表。

## 3. 持续回归入口

### 平台无关与当前开发环境

```bash
npm ci
npm run format:check
npm run check
npm test
```

`npm test` 必须覆盖 Renderer runtime、Zig serializer 与 TypeScript decoder 共用的投影 fixture、架构边界、AgentCore bundle 校验、child-process wrapper 和正式 Zig test graph。缺少 canonical staged bundle 时必须明确失败，不能跳过 AgentCore 相关用例后继续报告成功。

`npm run test:renderer-runtime` 中的 `scripts/scheduled-tasks.test.mjs` 持续固定定时任务一级入口、同级紧凑菜单、建议模板/自然语言创建、状态分区、detail/editor drawer、无 User Workspace 时的 default Text 创建、Skill 强制 explicit target 和 Bridge exact mutation payload；正式 Zig test graph 持续固定 recurrence、持久 store candidate commit/恢复、schema 1 tagged target 原地 hard cut、旧顶层 Workspace shape 判损坏、timer/missed-run 调度、binding 校验、凭据清洗，以及 occurrence 复用真实 Task/Run admission 的边界。

Managed Workspace 落地后，正式 Zig graph 必须固定 Native SDK `.data/workspaces` root capability、unavailable 降级、保留命名空间、随机独立目录、exclusive create/碰撞上限、canonical containment、user/managed 独立 record capacity、non-selecting registration、Session/Task 发布事务、发布前空目录回滚和 Task 删除 quiescence。跨语言 fixture、Renderer suite 与 lifecycle 必须固定 Workspace `origin`、Task → Workspace snapshot 引用完整、选择器/recent/操作过滤、managed Task route、定时任务 `default` 每个 occurrence 创建并保留不同 managed Workspace、`explicit` 只接受 User Workspace、后台 occurrence 不改变 User Workspace selection/recent/draft scope，以及 capability unavailable 时不静默采用用户目录。Windows bring-up 与 macOS 对应验证必须各自证明真实平台目录解析和权限行为；单元测试不能替代平台结果。

### macOS

首次使用真实 Account 前，按 [macOS 本地开发签名](macos-local-development.md)选择 Apple Development identity：

```bash
npm run setup:macos-signing
```

```bash
npm run build:debug
npm run build:release
npm run package:macos
```

`package:macos` 必须验证精确 Bundle ID `com.metask.metawork.dev`、产品版本、Apple-issued `TeamIdentifier` 与显式 canonical designated requirement，并由系统 requirement engine 独立复核 identifier、Apple anchor、Team 与所选 Apple Development certificate。架构回归必须证明各平台产品 Bundle ID 只来自 `app.zon`，macOS 使用 `MetaWork Dev` 与 `com.metask.metawork.dev.account`，Account store 独立拥有 `manifest.json` schema 1；Windows 使用同一产品 Bundle ID，但保持原 `MetaWork` 数据根目录、Credential Manager 与无版本 `account.json`。普通 check/test/build 不访问个人证书；`npm run dev` 和 `package:macos` 才使用本机选择；Account-owned legacy cleanup 只能由开发者显式执行。

Keychain 跨重建授权稳定性属于真实系统 UI 行为，不能由 `codesign` 或 package success 替代。当前状态为 **人工验收待完成**；验收必须在同一精确 commit 上依次完成：启动当前签名的 Debug app 并让 Account 写入/读取 `com.metask.metawork.dev.account`，完全退出，重新执行 `npm run dev` 产生并启动新构建，再次恢复 Account，并确认没有出现新的 Account Keychain 授权框。首次选择 Apple Development private key 时由 `/usr/bin/codesign` 触发的签名授权不属于 Account Keychain 失败。完成前不得把“签名验证通过”升级成“跨重建 Keychain 授权已验证”。

涉及 AgentCore candidate、正式 Host、Renderer reload、产品数据面或生命周期时，按变更范围增加：

```bash
AGENTCORE_BUNDLE_ROOT=/absolute/path/to/bundle npm run probe:agentcore
npm run test:lifecycle
npm run test:agentcore-vertical:macos
```

AgentCore vertical 是当前真实桌面自动化入口，同时验证真实 `ProductDelivery` 主线程 revision emit、Renderer reload、snapshot 恢复和 AgentCore Run；automation 不建立第二套 Renderer 数据面。一次性阶段聚合脚本和 fault-domain harness 不再保留。

### Windows development baseline

```powershell
npm run agentcore:stage -- C:\absolute\path\to\x86_64-windows.win10...win11_dt-gnu
npm run test:windows:bringup
```

macOS 与 Windows 结果不能互相替代。安装器、签名、更新、file dialog、process tree、timeout 和完整 security matrix 需要独立证据。

## 5. Renderer Bridge contract 验收

规范性策略见 [高层架构的 Renderer Bridge wire contract](architecture.md#71-renderer-bridge-wire-contract)。当前合同身份为 `metawork.renderer-bridge`，快速开发阶段固定 revision 为 `1`；合同内容原地 hard cut，snapshot 不维护局部版本，任何合同类版本标识变更必须先得到用户显式同意。

持续回归必须证明：

- connect identity/revision 匹配时才建立 product delivery connection；
- 未协商或 mismatch 时，Account、Task、event 和 snapshot 产品路径全部被现有门禁拒绝；
- 不兼容是 terminal bootstrap error，Renderer 不执行瞬时重试；
- Zig/TypeScript revision 与 command catalog 精确一致；
- Host serializer → TypeScript decoder、TypeScript command payload → Host decoder 均有跨语言 fixture/行为测试；
- snapshot 只由完整 Bridge contract revision 覆盖，不重新引入局部 schema version。
